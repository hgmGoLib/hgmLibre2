# 与标准库 `regexp` 怎么选

**结论先行:默认用本库。** 只有三种形状该留在标准库 `regexp` 上,而且这三种都能一眼认出来,
不需要先做实验:①运行期【现编】正则 ②过桥价级别的调用(输入只有几字节、正则简单到几乎不用扫)
③编译的是【别人写的】正则、语法面必须跟标准库逐字一致。除此之外,同一条正则同一份正文,
本库在本文的全部测量里没有输过 —— 最小 1.1 倍,常见 11~85 倍。

标准库 `regexp` 的匹配是从零重写的 NFA 模拟(onepass / bitstate 回溯 / 一遍 NFA),
只有能提出**字面量前缀**时才走 memchr 快路;提不出来就逐位置起头。本库是原生 RE2 的
惰性 DFA,一遍线性扫过,与正文形态无关。差距的来源就是这一条,不是"C 比 Go 快"。

---

## 0. 测量口径

本文每个数字都出自 `stdlib_compare_test.go`,重跑:

```sh
go test -run 'TestStdlibCompare' -v .
```

* 机器:AMD Ryzen 9 5900X · linux/amd64 · GOMAXPROCS=20 · go1.26.5
* 正文:100KiB × 16 份**互不相同**,三种形态 —— `prose`(英文散文,几乎不含 `"` `/`,
  是标准库前缀快路的**最好情况**)· `json`(满篇 `"` `{` `}` 的流式 JSON)· `dense`(全小写无空格)
* pattern 与语料都是**按形状合成的**,不取自任何具体调用方 —— 结论要按形状套用,不按业务套用
* 两个引擎每轮都先逐语料**对拍同解**,不同解直接 fail

🔴 **两档都要量**:「热缓存」(同一份正文反复扫)与「换语料」(每次一份新正文 = 产线形态)。
RE2 的 DFA 是懒构造的,单形状 benchmark 第二遍起一个状态都不再建。本文这批 pattern
两档基本没差(状态少),但表大了就会差到两个数量级 —— 见 [README#dfa-cache-thrashing](../README.md#dfa-cache-thrashing)。

## 1. 本库更快的情况

### 1.1 整篇正文(100KiB · 换语料档 · 英文散文 = 对标准库最有利的语料)

| 形状 | pattern | stdlib | 本库 | |
|---|---|---:|---:|---|
| **(?i) + 交替 + `\b`** | `(?i)alpha\s+(all\s+)?(beta\|gamma\|delta)\b` | 1890 µs | 22.3 µs | **84.8×** |
| **大小写不敏感的字面量** | `(?i)host\.example\.invalid/` | 1898 µs | 28.5 µs | **66.5×** |
| **多层可选的交替** | `(?i)(alpha\|beta\|gamma)\s+(delta\s+\|epsilon\s+(if\s+)?)?(zeta\s+(eta\|theta)\s+)` | 6095 µs | 141.7 µs | **43.0×** |
| **四段几乎全可选的交替** | `(?i)(alpha\|beta\|gamma)(the\|all\|your)?(delta)?(epsilon\|zetas?\|eta\|thetas?)` | 5109 µs | 142.6 µs | **35.8×** |
| **字符类 + 开区间计数重复** | `[A-Za-z0-9+/]{40,}={0,2}` | 4447 µs | 143.3 µs | **31.0×** |
| **交替:一支字面量一支带 `\b`** | `alpha_beta\|\bnew\s+Gamma\s*\(` | 2674 µs | 142.3 µs | **18.8×** |
| **查询串里取 key=value 的值** | `(?i)[?&](?:alpha[_-]?beta\|beta\|…)=[^&\s"']+` | 1680 µs | 142.5 µs | **11.8×** |
| **定长数字分组 + 两侧 `\b`** | `\b(?:\d{4}[- ]){3}\d{4}\b` | 1618 µs | 142.6 µs | **11.4×** |
| **纯字面量**(标准库能提前缀走 memchr) | `ZZQ-MARKER-42` | 1.21 µs | 1.05 µs | 1.15× |
| **JSON 字段值**(值里含转义) | `"(alpha\|beta)":"((?:[^"\\]\|\\.)*)"` | 1.19 µs | 1.07 µs | 1.12× |

一句话:**只要标准库提不出字面量前缀,差距就是一到两个数量级。** `(?i)`、`\b` 开头、
字符类开头、交替开头 —— 这四样任何一样出现在 pattern 开头,标准库的快路就没了。
提得出前缀的两行(最后两行)本库也没输,只是优势收敛到 1.1 倍上下 —— 那两行两个引擎实际都在跑 memchr。

### 1.2 语料形态会把"标准库看起来还行"的那两行掀掉

上表最后两行只在散文上成立,因为散文里几乎没有 `"`。换成真实的流式 JSON:

| pattern | prose | json | dense |
|---|---:|---:|---:|
| `"(alpha\|beta)":"((?:[^"\\]\|\\.)*)"` | 1.02× | **11.35×**(931 µs → 82.0 µs) | 1.15× |
| `[A-Za-z0-9+/]{40,}={0,2}` | 30.8× | 25.9× | **72.6×**(9.2 µs → 0.13 µs) |

🔴 **拿散文量出来的"打平"不能外推到产线。** 首字节越常见,标准库的 memchr 快路停得越频繁,
退化成逐位置重试;本库的 DFA 一遍扫完,三种语料上耗时基本是常数。
**量的时候语料必须跟调用点真正吃的东西同形态。**

### 1.3 几十字节的短输入(串行)

"输入短所以过桥价划不来"是**错的判断方式** —— 决定胜负的还是形状:

| 形状 | pattern | 输入 | stdlib | 本库 | |
|---|---|---|---:|---:|---|
| 锚定主机名校验 | `^(\*\.)?([a-zA-Z0-9]([a-zA-Z0-9-]{0,61}[a-zA-Z0-9])?\.)+[a-zA-Z]{2,}$` | 19B | 518 ns | 96 ns | **5.40×** |
| 锚定字符类校验 | `^[A-Za-z0-9_-]+$` | 19B | 289 ns | 98 ns | **2.95×** |
| 锚定定长十六进制 | `^[a-f0-9]{64}$` | 64B | 414 ns | 158 ns | **2.62×** |
| 锚定的字面量前缀交替 | `^(?:aa_\|bb_\|cc_\|…)` | 20B | 104 ns | 68 ns | 1.53× |

### 1.4 一次调用拿 N 条正则打同一条短串

6 条 `(?i)(--alpha[-_]?beta\s*[=:]\s*)('[^']*'\|"[^"]*"\|\S+)` 形状的替换正则,
打一条 161B 的命令行(全部不命中):

| | ns/op | Go 堆分配 |
|---|---:|---:|
| stdlib(`ReplaceAllString` + `${1}` 展开) | 24 886 | 2 216 B / 18 allocs |
| 本库(`ReplaceAllStringFunc`) | **1 021** | **0 B / 0 allocs** |
| | **24.4×** | |

6 次过桥(≈400ns)在这里完全不是问题,因为那 6 条形状标准库只能回溯。
**"短输入 = 该用标准库"这条经验法则本身是错的。**

## 2. 标准库更快的情况

### 2.1 过桥地板价:2 ns vs 67 ns

空输入上量一次调用的固定成本:标准库 **2 ns**,本库 **67 ns**(一次 cgo 过桥)。

所以:**如果一次匹配的真实工作量本身就在几十纳秒量级,过桥价就是全部成本。**
典型是"几字节输入 + 简单到不用扫的正则"。注意 §1.3 那四行都是几十字节输入,
本库照样赢 1.5~5.4 倍 —— 地板价只有在**匹配本身比 67ns 还便宜**时才决定胜负。

### 2.2 编译:标准库快 1.2~4.6 倍

| pattern | stdlib | 本库 | | stdlib 分配 | 本库分配 |
|---|---:|---:|---|---:|---:|
| `^(\*\.)?([a-zA-Z0-9](…)?\.)+[a-zA-Z]{2,}$` | 26.0 µs | 51.6 µs | 1.99× | 46 456 B / 278 | 384 B / 3 |
| `[A-Za-z0-9+/]{40,}={0,2}` | 4.4 µs | 20.0 µs | **4.59×** | 8 504 B / 35 | 336 B / 3 |
| `(?i)…(delta\s+\|epsilon\s+(if\s+)?)?…` | 9.9 µs | 24.0 µs | 2.44× | 11 728 B / 95 | 416 B / 3 |
| `ZZQ-MARKER-42` | 1.7 µs | 3.0 µs | 1.78× | 2 176 B / 20 | 336 B / 3 |

编译成本对**包级变量**来说是进程启动一次性的:110 条全用本库,启动多付约 3 ms,
换来的是每次匹配都不再回溯 —— 不用犹豫。注意 Go 堆分配是**反过来**的:
标准库一条正则常驻 2~46 KB Go 堆,本库恒 336~416 B(实体在 C 侧)。

### 2.3 运行期【现编】正则 —— 这一档必须留标准库

每次调用现编一条 `(?i)\b<词>\b` 再打一句 90B 的话(典型:按关键词表逐词造正则):

| | ns/op | Go 堆分配 |
|---|---:|---:|
| stdlib | **9 205** | 11 350 B / 85 allocs |
| 本库 | 21 568 | 400 B / 4 allocs |
| | **stdlib 快 2.34×** | |

编译价直接进热路径,而这一档的匹配本身只有几百纳秒,赢不回来。
**能提到包级变量就提;提不了(词表是运行期来的、且不缓存)就用标准库。**
—— 或者反过来想:这一档真正的解法是**把 N 个关键词编成一个 `RegexpSet` 扫一遍**,
那就又回到本库了,见 [README#regexpset](../README.md#regexpset)。

### 2.4 短输入 + 高并发 = 打平区间(不是标准库的胜场,但也不是本库的)

共享一个 `*Regexp`,往上加 goroutine(锚定主机名校验 · 19B 输入):

| goroutine | stdlib | 本库 |
|---:|---:|---:|
| 1(串行) | 518 ns | 96 ns |
| 20 | 54~55 ns | 39~79 ns |
| 200 | 51 ns | 40~44 ns |
| 1000 | 50~51 ns | 36~45 ns |

🔴 **本库串行时 5.4 倍的优势,到 20 goroutine 就基本被吃光。** 原因是本库每次搜索要拿一次
DFA 状态缓存的读锁(见 [README#concurrency](../README.md#concurrency-sharing-one-regexp-is-fine-it-just-doesnt-scale-linearly)),
标准库没有这把锁:标准库拿到约 10 倍并发加速,本库只拿到 2~3 倍。
上表 20 goroutine 那一格**跨轮不稳定**(三轮分别是本库 79 / 39 / 39 ns),
两个引擎在 ±1.5 倍内互有胜负 —— 结论只能写成"打平",谁也别声称赢。

**同一把锁在整篇正文那一档完全不是问题**:一次搜索的活多到锁的占比可以忽略,
1000 goroutine 下本库仍快 **100 倍**(202.6 µs vs 2.01 µs)。

## 3. 内存

### 3.1 每次匹配的 Go 堆分配:本库恒 0

| | 100KiB 正文匹配一次 | 6 条正则替换一条 161B 串 |
|---|---|---|
| stdlib | 3~39 B/op | 2 216 B / 18 allocs |
| 本库 | **0 B / 0 allocs** | **0 B / 0 allocs** |

匹配全在 C 侧做,不经过 Go 堆 ⇒ **不抬高 GC 堆目标**。GOGC 制度下这才是峰值真正说了算的东西。

### 3.2 进程内存峰值(VmHWM · 一条路一个子进程各报)

110 条包级正则(上面 10 种形状 × 11 份):

| | 只编译不扫 | 再扫 16×100KiB 最坏形状语料 |
|---|---:|---:|
| stdlib | +0.93 MB | +0.16 MB |
| 本库 | **+0.79 MB** | +1.68 MB(`DFAStats().Resets = 0`) |

读法:**常驻这一格本库还略省**(正则实体在 C 侧,比标准库的 Go 侧程序表小)。
扫起来之后多出来的 ~1.5 MB 是 DFA 状态缓存 —— 这是本库拿内存换时间的地方,
110 条正则的量级上完全不值得纠结。

⚠ 但这一格**会随 pattern 形状爆炸**,不能外推:`S B{m,n} L` 那类
(起始类窄于重复类的计数重复)正向 DFA 状态数对界指数增长,单条就能吃掉几 MB。
真怕内存就量 `Resets`(`>0` 就是在 thrash)和 `MemInfo()`,别猜;
形状允许的话**换个方向扫比调预算便宜**,见 [README#scanning-backwards](../README.md#scanning-backwards)。

## 4. 本库缺什么(迁移前先过这张表)

本库**不是** `*regexp.Regexp` 的 drop-in,也不打算是。下面是全部缺口,
前两条是 API 设计取舍,后面是引擎差异。完整版见 [README#supported-api](../README.md#supported-api) 与
[README#differences-from-stdlib-regexp](../README.md#differences-from-stdlib-regexp)。

**编译期就会挡住你的(改代码才能迁):**

| 缺什么 | 怎么办 |
|---|---|
| `ReplaceAllString` 的 `$1` / `${name}` / `$$` **不展开**(repl 是字面) | 改用 `ReplaceAllStringFunc` 自己拼;或用非 stdlib 的 `FindReplaceWithin`(它用 RE2 的 `\1` rewrite 语法) |
| `ReplaceAllLiteralString` / `Expand` / `ExpandString` | 没有;分别等价于本库的 `ReplaceAllString` / 自己拼 |
| `io.Reader` 系(`MatchReader` / `FindReaderIndex` / `FindReaderSubmatchIndex`) | 没有;先读进 `[]byte` 再用 `[]byte` 系(**任何长度都不产生拷贝**) |
| `SubexpIndex` | 没有;用 `SubexpNames()` 自己找下标 |
| `LiteralPrefix` | 没有;要"必需字面量"用 `NewPrefilter`(比 `LiteralPrefix` 强得多,见 [README#prefilter](../README.md#prefilter-which-literals-must-appear-and-which-patterns-can-never-be-filtered)) |
| `Longest()`(leftmost-longest 模式) | 没有;本库恒 leftmost-first,与 `regexp.Compile` 默认一致 |
| `Copy` / `MarshalText` / `UnmarshalText` | 没有 |
| 包级便捷函数 `regexp.MatchString(pat, s)` / `regexp.Match` | 没有;自己 `MustCompile` 一次存包级变量(本来就该这样) |

**编译得过但语义会变的(危险,必须逐条查):**

| 差异 | 什么时候会咬人 |
|---|---|
| **非法 UTF-8**:标准库把每个非法字节当一个 `U+FFFD` 让 `.` 匹配,本库(原生 RE2)只匹配完整合法 rune | 输入可能非法 UTF-8 且靠 `.` 兜底时。**要标准库的行为就留标准库** |
| **语法面不同**:`\C` 本库接受、标准库拒绝;个别 escape 只有一边认;本库**无嵌套深度上限**(标准库 1000 层就报错);捕获组名可以非 ASCII | 编译的是**用户/配置提供的正则**时 —— 换引擎 = 换用户可写的语法面。如果同一条正则还要在别处用标准库编译,两边必须同引擎,这是**语义契约**不是性能问题 |
| **大小写折叠**:被并进字符类的折叠字面量会折满整个 Unicode orbit(`\w\|[kK]` 也匹配 U+212A) | `(?i)` + 交替 + 非 ASCII 折叠等价字符 |
| **2 GiB 输入上限**:超过按"不匹配"处理 | 喂多 GB 正文时 |
| **`[]byte` 替换系无改动时复用 `src`**(零分配),标准库总是返新切片 | 拿返回值当可写缓冲用时 —— **不得改写返回值**,要可写自己 copy |

**构建面:** 需要 cgo(**必须开启**)与一个 C++11 编译器(clang / gcc / `zig c++` 都行)。
不下载任何远程源、不需要 abseil / CMake,可用 zig 交叉编译。纯 Go 构建 / `CGO_ENABLED=0` 的场景用不了本库。

## 5. 一页判据

```
这条正则是在【运行期现编】的、且编出来不缓存吗?
  是 → 标准库。(更好的做法: 提到包级变量, 或者把 N 条编成一个 RegexpSet)
  否 ↓
它编译的是【别人写的】正则、语法面必须和标准库逐字一致吗?
  是 → 标准库。这是语义契约, 与性能无关。
  否 ↓
需要 $1 展开 / io.Reader / Longest / SubexpIndex / 非法 UTF-8 上的 U+FFFD 行为吗?
  是 → 看 §4 那张表: 大多数能改写, 改不了的留标准库。
  否 ↓
一次匹配的真实工作量比 67ns(过桥价) 还小吗?
  (= 输入只有几字节, 且正则简单到 onepass 一遍就完)
  是 → 两边都行, 差别在噪声里, 别折腾。
  否 → 【用本库】。
```

补两条**不是判据**的经验法则,它们会把人带沟里:

* ❌ **"输入短所以用标准库"** —— §1.4 那格 161B 输入 6 条正则,本库快 24 倍且零分配。
  决定胜负的是**形状**(标准库要不要回溯),不是长度。
* ❌ **"有字面量前缀所以标准库更快"** —— §1.1 最后两行本库也没输(1.1 倍),
  而且这条经验只在**首字节在正文里很罕见**时才成立;换成真实 JSON 就是 11 倍(§1.2)。

## 6. 这些结论的有效边界

* 全部数据来自**一台机器一个平台**(Ryzen 5900X · linux/amd64 · go1.26.5)。
  过桥价(67 ns)与编译价随平台/Go 版本漂移,**§2.1 和 §2.3 这两档换平台要重量**;
  §1 那些 10 倍以上的差距是算法级的(DFA vs 回溯),不会因为换机器翻盘。
* pattern 是**按形状合成的**。真表里如果有 `S B{m,n} L` 那类状态数对界指数的形状,
  §3.2 的内存结论不适用 —— 那种要单独量 `Resets` / `MemInfo()`,并考虑反着扫。
* 本文只比了**单条 `Regexp`**。N 条正则要一起扫的话,正确的比较对象根本不是"N 条标准库正则",
  而是一个 `RegexpSet`(一遍 DFA 回答"哪几条命中"),那是另一个数量级的话题 ——
  见 [README#regexpset](../README.md#regexpset) 与 [set性能优化经验.txt](set性能优化经验.txt)。
