hgmLibre2 RegexpSet 状态数为什么会【相乘】—— 给【调用者】看的
================================================================================
配套阅读: 同目录 set性能优化经验.txt (那篇讲"量什么、调什么", 本篇只讲一件事:
          一张表的状态数是怎么从各条 pattern 的代价里长出来的, 以及为什么它不是加法)。

本篇是对那篇 §3.3 那句「组合确实超可加, 但只有 1.25~1.59 倍」的**修正加细化**:
那个区间只在"表里每条 pattern 自己都便宜"时成立。只要表里**有一条状态数上万的**,
超可加系数会从 1.5 跳到 3, 而且更要命的是 —— 一条**自己只值 55 个状态**的 pattern,
放进那张表里会**多造出十一万个**。代价不是 pattern 自己的属性, 是它和邻居的乘积。

下面所有数字都可以自己复现: 3 条合成 pattern + 1MB 合成语料 (壳是压缩过的 JS,
里面撒着长 base62 token —— 就是"标识符里字母数字随机交错"这个形态), maxMem 512MB,
全程 flush = 0 (刻意把 flush 这个变量消掉, 只看状态数本身)。


================================================================================
零、先看这四句
================================================================================
1. **一个 DFA 状态 = 「窗口里还悬着哪些起点、各自走到第几步」这件事的一份快照。**
   一张 Set 里所有 pattern 共用同一个状态集, 各自的"悬着什么"是**独立**演化的
   ⇒ 组合起来是**笛卡尔积**, 不是并集。这就是相乘的全部原因。
2. 所以 **一条 pattern 的代价永远只能在【它所在的那张表】里谈**。单独 benchmark 一条
   pattern 说"它才 55 个状态, 很便宜"是没有意义的 —— 它是乘数里的一个因子。
3. **乘数从哪来**: 绝大多数 pattern 的"悬着的起点"是【最近 k 个偏移】这一整段连续后缀,
   只有 k+1 种可能, 所以它们是小因子。**只有一种形状会变成大因子**:
   计数重复 `S B{m,n}` 里 **起始类 S 严格窄于重复类 B** ⇒ 存活起点退化成"任意子集" ⇒ 2^k 级。
   实测同一条 pattern 只改首字符类, 状态数差 **1037 倍**。
4. **惰性缓存救了你, 但只救一半**。理论笛卡尔积是 7500 万, 实际只缓存了 17.8 万 (0.24%),
   因为语料走不到其余的。所以"理论状态数"这个词对 hgmLibre2 基本没有参考价值 ——
   **但那 17.8 万已经是 76MB 和 10 倍吞吐损失了**。


================================================================================
一、实测: 同一条 pattern, 换个邻居, 代价差 1250 倍
================================================================================
三条 pattern (都是合成的, 形状取自现实里常见的几类):
    A  [A-Za-z0-9]{52}CASK[A-Za-z0-9]{28}          定长 base62 + 中缀标记
    B  [A-Za-z0-9_-]{20,}KEYMARK[A-Za-z0-9_-]{20,}  变长 base64url 夹标记
    C  [A-Za-z][A-Za-z0-9]{2,19}key                【病灶形状】首字符类窄于重复类
    C' [A-Za-z0-9][A-Za-z0-9]{2,19}key             C 的健康版: 首字符类 = 重复类

    表        状态数    已用     每状态   稳态吞吐   相对"各自单跑之和"
    A            55    0.01MB    214 B   674 MB/s
    B            24    0.00MB    160 B   675 MB/s
    C'           55    0.01MB    153 B   666 MB/s
    C         57042    9.20MB    161 B   266 MB/s      ← 一条就病了
    ------------------------------------------------------------------------
    A+B         115    0.04MB    330 B   666 MB/s      79   → 1.46×
    A+C'        148    0.04MB    298 B   649 MB/s      110  → 1.35×
    A+B+C'      208    0.08MB    404 B   655 MB/s      134  → 1.55×   健康表: 就是那 1.25~1.59
    ------------------------------------------------------------------------
    B+C       71683   18.98MB    265 B   207 MB/s      57066 → 1.26×
    A+C      173256   56.81MB    328 B    94 MB/s      57097 → **3.03×**
    A+B+C    177538   75.77MB    427 B    65 MB/s      57121 → **3.11×**

🔴 把两行摆在一起看, 这是本篇的全部内容:
       把 A 加到【健康】的表上:  C'  55 → A+C'   148    A 带来 **+93** 个状态
       把 A 加到【病了】的表上:  C 57042 → A+C 173256    A 带来 **+116214** 个状态
   同一条 A, 代价差 **1250 倍**。A 自己单跑只有 55 个状态, 它在病表里带来的增量
   是它单跑成本的 **2113 倍**。
   B 同理: 单跑 24 个, 加到 C 上带来 +14641 个 (**610 倍**)。

   ⇒ 推论 1: 排查"谁贵"时, **单跑一条一条量是错的方法**。要做**留一消融**
     (逐条摘掉再量全表), 差值才是它的真实成本。
   ⇒ 推论 2: 一张表里只要混进一条病的, **其余所有 pattern 的账单一起翻几百倍**。
     修一条的收益远大于删十条。


================================================================================
二、为什么是乘法: 状态到底是什么
================================================================================
非锚定搜索 (从任意偏移都可能开始匹配) 下, DFA 走到第 i 个字节时必须记住:
「到目前为止, 有哪些更早的偏移仍然可能是一次匹配的起点, 而且它们各自走到了第几步」。
这整件事被压缩成**一个整数** (状态在缓存里的下标) —— 这就是 DFA 快的原因,
每字节只做一次查表; 也是它贵的原因: **每一种不同的"悬着什么", 都必须是一个不同的整数**。

两条 pattern 放进同一张 Set:
    状态 = (P1 悬着什么, P2 悬着什么)
两者互不影响地各自演化, 所以可区分的组合数 = |P1 的可能| × |P2 的可能|。
**乘法就是从这里来的, 没有别的机制。**

对应到上表: A 有 55 种, C 有 57042 种, 上限 55 × 57042 = 3137310。


================================================================================
三、大因子只有一种形状: 起始类 ⊊ 重复类
================================================================================
对 `S B{m,n} LIT` 这一族:

  · **S = B** (如 `[A-Za-z0-9][A-Za-z0-9]{2,19}key`): 每个字节都能开一个新起点,
    所以"还活着的起点"永远是【最近 k 个偏移】这**一整段连续后缀** —— 只有 k+1 种
    ⇒ **k+1 个状态**, 是个小因子。
  · **S ⊊ B** (如 `[A-Za-z][A-Za-z0-9]{2,19}key`): 只有字母位置能开起点, 数字位置不能。
    于是存活集合变成"最近 k 个偏移里, 哪几个当时是字母"—— 一个**任意子集** ⇒ 最坏 **2^k**。
    正文里字母/数字随机交错时 (压缩 JS、长 token、hash、base64), 这些子集会被走个遍。

实测 (同一份 1MB 语料, 单条 pattern):
    pattern                              状态数    已用      吞吐     说明
    [A-Za-z][A-Za-z0-9]{2,19}key         57042   9.20MB   264 MB/s  病灶
    [A-Za-z0-9][A-Za-z0-9]{2,19}key         55   0.01MB   666 MB/s  首字符放宽 ⇒ **1037×**
    \b[A-Za-z][A-Za-z0-9]{2,19}key          59   0.01MB   666 MB/s  词首守卫 ⇒ **967×**
    [A-Za-z][A-Za-z0-9]{2,}key              11   0.00MB   660 MB/s  去掉上界 ⇒ **5185×**

🔴 **计数长度本身不是引爆点, "谁能当起点"才是。** 但上界确实决定 k, 所以它是指数的底数上的指数:
    {2,3} → 24 个    {2,9} → 759 个    {2,19} → 57042 个    {2,39} → 458107 个 (104MB)
   注意最后一档只涨了 8 倍而不是 2^20 倍 —— 那是第四节的惰性缓存在兜底, 不是它不该涨。

为什么 `\b` 管用: 词首守卫让"能开起点的位置"退化成极稀疏一集 (一个词只有 1 个),
同时悬着的起点最多一两个, 子集根本长不起来。

为什么 `{2,}` 管用: **无上界的重复不需要计数**。`X*` / `X+` 在自动机里是一个自环,
不摊拷贝, 也就没有"走到第几步"这个维度。这是 `{2,}` 只有 11 个状态而 `{2,19}` 有 57042 个的原因。

⚠ **两种改法方向相反, 上线前必须分清**:
    `\b`   是**收窄** —— 原来能命中的一部分会不再命中 (例: 超长标识符的尾部子串)。
    `{2,}` 是**放宽** —— 是原语言的**超集**, 只会多报, 不会漏报。
  如果这张 Set 是当"必要条件门"用的 (先粗筛, 再用完整规则复核), `{2,}` 是安全的;
  如果它的命中结果直接当最终答案, 两种都要拿真语料对拍命中集。


================================================================================
四、惰性缓存: 它救了你多少, 又为什么救不完
================================================================================
hgmLibre2 底下的 DFA 是**惰性**的: 状态不是编译期全部枚举出来, 而是**正文走到哪造到哪**,
只缓存**实际出现过**的状态。所以"理论状态数"这个词对调优基本没用 —— 实测:

    表       理论上限 (各因子相乘)    实际缓存      实现率
    A+B            55 × 24 = 1320          115       8.7%
    A+C'           55 × 55 = 3025          148       4.9%
    B+C        24 × 57042 = 1369008      71683       5.2%
    A+C        55 × 57042 = 3137310     173256       5.5%
    A+B+C   55 × 24 × 57042 = 75336240  177538      0.24%

⇒ 结论 1: **惰性把指数压成了"语料实际走过的路径数"**, 表越大压得越狠 (0.24%)。
   所以不要因为"理论上 2^19" 就吓得不敢写计数重复 —— 决定账单的是**你的正文形态**。
⇒ 结论 2: **但它压不到零。** A+B+C 那 0.24% 仍然是 17.8 万个状态、76MB、吞吐掉 10 倍。
   惰性缓存把"必然 OOM"变成了"看语料脸色", 它不是一个修复。
⇒ 结论 3 (最实用的一条): **换一份语料, 账单会变个数量级**, 而且方向常常反直觉。
   同一批 pattern 换成等体量的英文散文语料, 上面那张 A+B+C 只造 **10 个状态** (差 17754 倍)。
   ⇒ **绝不要拿"我们线上跑得挺好"当结论**, 那只说明当前流量没走进那些子集。
     要专门造一份"字母数字随机交错的长 token"语料当**压力样本**去量。


================================================================================
五、自查清单 (不用跑语料, 看 pattern 就能筛)
================================================================================
把表里每条 pattern 的 AST 过一遍, 满足下面全部条件的就是**大因子嫌疑**:

  1. 有一个**有上界**的计数重复 `X{m,n}` (或 `{n,}` 但 n 很大), 上界 ≥ 8;
  2. 重复的那个字符类**宽** (能吃 ≥32 个不同字节, 如 base62 / base64url / 十六进制);
  3. 它**前面紧挨着**的那个字符类也宽 (≥16), 但**严格窄于**重复类  ← 这条是关键;
  4. 这段重复之前**没有**够长的字面量前缀 (≥3 个字符) 当守卫;
  5. 这段重复之前**没有** `\b` / `^` 守卫。

三条**不用报**的 (省得误杀):
  · `*` / `+` / 大 `{n,}`: 无上界的重复不摊拷贝 (见 §3)。
  · 前面有字面前缀的: `AIza[A-Za-z0-9_-]{35}` 这种, 只有字面命中之后才走得进去。
  · 前面有 `\b` / `^` 的: 起点已经稀疏了。

⚠ 这份清单查的是**形状**, 不是**代价**。代价永远只能拿你自己的真语料标定 ——
  形状对上了但你的正文从不走进去, 它就是免费的 (见 §4 结论 3)。

量代价的正确姿势 (三步, 配合 set性能优化经验.txt §2 的读数):
  1. 把 maxMem 调到 flush = 0, 否则量到的是抖动不是状态数;
  2. 全表跑一遍, 记 MemInfo().States 和 Used();
  3. **逐条摘掉**再跑全表, 差值 = 这条的真实成本。**不要单跑一条来估**(见 §1 推论 1)。
  N 条要跑 N+1 遍, 但这是唯一能读出因果的方法。


================================================================================
六、能做什么 (按 收益/成本 排)
================================================================================
A0. **先看能不能反着扫** —— 这一族 pattern 的必需字面量在尾巴上, 反过来读它就变成首部守卫,
   起点立刻稀疏 (实测 35149 → 45 个状态), 而且**命中集一个字节不变**, 不用去说服规则作者。
   API 是 CompileReverse (得到一个单独的 *RegexpReverse 对象) / NewRegexpSetReverseMaxMem,
   用法与三条注意事项见 set性能优化经验.txt §4A。
   **要位置也不用再正向扫一遍**: RegexpSetReverse.NewMatchScanner() 一遍扫直接给不重叠的
   命中区间 (口径 rightmost-longest · 区间按 Lo 降序 · 见 doc/MatchScanner的leftmost-longest保证.md
   第 8 节)。单条 RegexpReverse 那边仍然只回答"命中没有", 拿它当门, 命中的那极少数再正向跑一次。

A. **改那一条 pattern** —— 不能翻方向时收益最大, 成本最低。
   给病灶分支加 `\b`, 或把 `{m,n}` 的上界去掉写成 `{m,}`。一个字符的改动,
   在实测里是 1000 倍状态数 + 2.5 倍吞吐。注意 §3 那条方向性警告。

B. **给每个分支留一个真实的字面量锚点。** 由字符类而不是字面量驱动的分支, 代价随语料的
   字母表走, 会在你没预料到的语料上炸 —— 而且它同时躲不掉任何预筛。
   (这与 set性能优化经验.txt §3.6 是同一条规律的两个面。)

C. **拆表要拆得对**: 把那**一条病的**单独拿出去 (哪怕它自己还是 57042 个状态),
   剩下 N-1 条立刻塌回几百个 —— 因为乘数没了。
   反过来, 按"条数"均匀对半拆是**没用的** (乘数还在其中一片里)。
   ⚠ 拆表另有代价, 先读 set性能优化经验.txt §5, 那节说明了为什么均匀拆常常是亏的。

D. **抬 maxMem** 只是把 flush 悬崖推远, 它一个状态都不会少造, 吞吐也救不回来
   (上表全程 flush=0, 65 MB/s 是纯粹的缓存未命中)。它是止血, 不是治疗。

E. 不要试的: 想办法"让单个状态便宜点"。每状态字节数在上表里从 153 到 427 只差 2.8 倍,
   而状态数差了 3000 倍。钱全在数量上。(同 set性能优化经验.txt §3.2。)


================================================================================
七、一页速查
================================================================================
· 一张 Set 的状态数 ≈ 各条 pattern "可能悬着什么"的**乘积**, 被语料实际走过的路径数截断。
· 绝大多数 pattern 是小因子 (k+1 种)。大因子只有一种形状: **计数重复的起始类严格窄于重复类**。
· 一条 pattern 的代价只在它所在的表里成立。**单跑量出来的数没有意义, 要用留一消融。**
· 修一条病的 > 删十条好的。
· 惰性缓存把指数压到 0.2%~9%, 但压不到零; 它让账单**取决于语料形态**, 所以必须专门造压力样本。
· `{m,n}` → `{m,}` 是超集 (安全, 只多报); 加 `\b` 是收窄 (会丢命中, 要对拍)。
