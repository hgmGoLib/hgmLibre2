# 已有库的坑

选型时踩过/量过的坑,记在这里省得下次再走一遍。

---

## re2c / re2go(AOT 生成 DFA 代码)

**结论:想拿它替掉运行期正则引擎,做「一批正则同时扫一段文本」这件事,不行。**
否掉它的不是性能,是**表达能力**和**语义**。下面是实测数据(darwin/arm64 ·
re2c 4.5.1 · go1.25 · clang -O2),样本是某项目运行期 dump 出来的 351 条正则,
正文 16MiB。

### 坑 1:一多半正则根本翻译不了

re2c 是**词法器生成器**,不是正则搜索引擎,它的语法缺一大块:

| 缺什么 | 351 条里受影响 |
|---|---|
| `\b` `\B` 词边界(没有任何零宽断言) | **193 条** |
| `^` `$` 锚(词法器天然在游标处匹配,没有"行首"概念) | 8 条 |
| 惰性量词 `*?` `+?` `{n,m}?` | 4 条 |
| `\p{...}` Unicode 类 | 3 条 |

合计 **208 / 351 条翻不过去**,而且 `\b` 这条**无解** —— 它不是"写起来麻烦",
是自动机模型里表达不出来。硬要模拟只能把前后的非词字符吃进匹配里,
那匹配边界就错了。

能翻的部分要注意:

- `(?i)` / `(?i:...)` **能**准确表达 —— re2c 的**单引号串是大小写不敏感的**
  (`'abc'`),双引号串是敏感的(`"abc"`),而**字符类不受影响**,
  正好对上 RE2 的语义。别去用全局的 `--case-insensitive`,那个粒度是错的。
- `\d` `\s` `\w` 要手工展开成字符类;`(?:` 写成 `(`(re2c 的括号本来就不捕获)。
- 非 ASCII 必须开 `re2c:encoding:utf8 = 1;`,否则报
  `error: bad code point: '0x62AB'`。
- `re2c:eof = 0` 要求**正文末尾多带一个 0 字节做哨兵**,`lim = len(str)-1`。
  不给哨兵就是越界读(Go 里 panic,C 里 UB)。

### 坑 2:AOT 的 DFA 会真的爆,而且爆得很早

把能翻的 143 条往一个词法器里塞,逐条加:

| 规则数 | 生成的 Go 代码 | re2go 耗时 | 峰值内存 |
|---|---|---|---|
| 10 | 12 966 行 / 0.26 MB | 0.01s | 8 MB |
| 20 | 347 482 行 / 6.25 MB | 0.27s | 129 MB |
| 35 | 376 250 行 / 6.95 MB | 0.37s | 171 MB |
| 40 | ❌ `re2go: error: DFA has too many states` | | |

跳过塞不进的继续贪心到底,**一个 DFA 最多容得下 61 / 143 条**。
撑爆它的是这几类(都很常见):

- 字母之间允许若干分隔符的"抗混淆"写法 `a[\s\-]{0,3}b[\s\-]{0,3}c…`;
- 大区间的计数重复 `[A-Za-z0-9+/_\-]{4,128}(…)+`;
- UTF-8 下的负字符类 + 计数重复 `[^X\n]{0,8}` —— 负字符类在 UTF-8 里本身
  就是一台多字节自动机,再乘计数重复就炸了。

**对比 RE2:同样这 143 条,一个 `RegexpSet` 全装得下,编译 9ms。**

根本区别在于 **RE2 的 DFA 是懒构造的** —— 只实例化实际输入上可达的那些状态;
re2c 必须在生成期把整张表全展开。所以"DFA 爆了"在两边根本不是一回事:

- RE2 爆在**编译期程序预算**(`RE2::Options` 默认 `max_mem = 8MB` 喂给
  `Prog::CompileSet`),把正则拆成几个 `RegexpSet` 就绕开了;
- re2c 爆在 **AOT 状态数**,绕不开。

### 坑 3:构建代价高到不能接受

35 条规则(占那批正则的 10%)的生成物:

| | 代码量 | 生成 | 编译 | 二进制 |
|---|---|---|---|---|
| re2go → `go build` | 376 250 行 / 6.95 MB | 0.37s | **4 分 51 秒** | 9.4 MB |
| re2c → `clang -O2` | 770 838 行 / 10.3 MB | 0.45s | **2 分 36 秒** | 5.6 MB |

10% 的规则换 5 分钟编译。注意 re2c 生成得很快(不到 0.5 秒),**慢的是下游编译器**
被几十万行 switch/goto 撑住,所以指望"生成器优化一下"是没用的。

### 坑 4:性能由正文形态决定,最坏形态下慢一到两个数量级

同一批 35 条规则,16MiB 正文:

| 引擎 | 全 `'x'` 的正文 | 英文散文 |
|---|---|---|
| RE2 `RegexpSet.Match` | **24.0 ms**(1.50 ms/MiB) | 25.5 ms(1.59 ms/MiB) |
| re2c(C, -O2) | 700.5 ms(43.78) **慢 29×** | **8.7 ms**(0.55)快 2.9× |
| re2go(Go) | 1081.7 ms(67.61) **慢 45×** | 11.8 ms(0.74)快 2.2× |

散文上确实比 RE2 快 2~3 倍,但这个优势**不稳定**:词法器每次匹配失败就把游标
+1 从头再来。散文里落进 `[A-Za-z0-9…]` 这类字符类的游程只有 4~5 字节,所以很快;
换成一大段全在字符类里的字节(上表的全 `'x'`),每个起点都要往前吃几十字节才失败,
退化成 O(n·m)。**RE2 一遍扫完,与正文形态无关**,稳定在 1.5 ms/MiB。

顺带:同样的规则,re2go 生成的 Go 代码比 re2c 生成的 C 慢 1.5~2.3 倍。

### 坑 5(最要命):语义不等价,会静默漏报

即使只用能翻译的那部分规则,结果也**对不上**。同一份 16MiB 散文、同一批 35 条规则:

```
RE2 RegexpSet 命中: [15 20 39 40 42]
re2go         命中: [15 39]          ← 漏 3 条
```

两个漏因都是词法器形态自带的,**不是翻译没做好**:

1. **命中后游标跳到匹配末尾**。起点落在被跳过区间里的其它规则,就再没人看了。
2. **规则之间有优先级,后面的会被前面的遮蔽**。re2go 自己会警告:
   `warning: unreachable rule (shadowed by rules at lines 30, 33)` ——
   这个警告务必当错误看。

要严格等价于"这 N 条里哪几条在正文任意位置出现过",只能**每个位置都重启一次**
= O(n·m),16MiB 上根本跑不完。

## 什么时候 re2c / re2go 仍然是对的

上面全是"拿它当搜索引擎"的坑。它本职工作没问题:

- 规则数**十条以内**、彼此**互斥**、天然就是**分词**语义(编译器 lexer、
  协议头解析、日志行切分);
- 输入是**逐 token 消费**的,不需要"在任意位置搜索";
- 不需要 `\b` / 锚 / 惰性量词。

这种场景下它的确比运行期正则快,而且零依赖零启动开销。
一旦你的需求是"一堆正则,扫一段文本,报哪几条命中",就用 `RegexpSet`。
