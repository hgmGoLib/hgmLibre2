hgmLibre2 RegexpSet 性能优化经验 —— 给【调用者】看的
================================================================================
这份文件写给"手里有一张几百条正则的表, 要用 RegexpSet 一遍扫完正文"的人 (或 AI)。
只讲【调用方能做什么、该量什么数、改哪里有用】, 不讲库内部怎么实现的。
库内部的改动记录在本仓库之外的分析项目里, 与调优无关。

所有数字都是在一张 223 条真规则表 + 2.66MB 真语料上量出来的, 不是合成数据;
换你自己的表和语料, 绝对值一定不同, 但下面每一条【结论的方向】都复现过多份语料。


================================================================================
零、先看这三句
================================================================================
1. 慢不慢, 只取决于一件事: **DFA 要不要现造状态**。造状态比走缓存慢两个数量级。
   flush (缓存被整表清空) 只是"造状态"的一个诱因, 它本身只贵 1.3~2.8 倍, 不是主因。
2. 造状态多不多, 主要取决于 **pattern 里"前一个关键词 …中间容忍 N 个任意字符… 后一个关键词"
   这种容差窗口有多宽、正文有多频繁地走进这些窗口**。跟"正文看起来有多乱/熵多高"无关。
3. 调优的第一步永远是 **量, 不是猜**。库提供了三个读数 (§2), 五分钟就能知道你在哪一档。


================================================================================
一、心智模型: 两条天花板 + 一道悬崖 + 一个上限
================================================================================
1.1 maxMem 是一个旋钮, 同时抬两条完全不同的天花板
    · 【编译期】整张表的 NFA 指令条数上限。撞了 = NewRegexpSet 直接返回 error
      ("set compile failed (out of memory)")。这是唯一会报错的地方。
    · 【运行期】剩下的额度给 DFA 状态缓存。撞了 **不报错**: 缓存整表清空重来, 结果照样正确,
      只是变慢。调用方在 API 上收不到任何信号。
    ⇒ "能编过" ≠ "预算够"。前者只清了第一条天花板。

1.2 编译期撞墙时: 不要把表拆成两个 Set
    两个 Set = 正文扫两遍, 比多给几十 MB 内存贵得多。做法是 NewRegexpSetMaxMem 把预算翻倍
    (8 → 16 → 32 → 64MB) 直到编过。构建期一次性开销, 之后 Set 只读、并发安全。
    ⚠ 这条只管编译期。如果表是在运行期真的 thrash (§2 量到 Flushes>0), 拆片反而可能更快 —— 见 §5。

1.3 运行期的悬崖长什么样
    同一张 223 条表, 同一批正文, 只改预算:
        预算 64MB → 0 次 flush → 291 MB/s
        预算 32MB → 每轮几次 flush → 2.6 MB/s
    差 113 倍。中间没有过渡带 —— 差一点点预算就整个掉下去。所以它是【够/不够】的二值问题,
    不是"多给点内存快一点"的连续问题。**不要试图给"刚好够"的预算, 要给"确定够"的预算。**

1.4 但缓存救不了新正文 —— 这条最容易被忽略
    在完全不 flush 的 64MB 档:
        第 1 轮 (全新语料) 每份 80KB 正文 23.7ms
        第 2 轮 (同一批正文重扫, 一个状态都不新建) 每份 0.36ms
    **66 倍**, 而且全程 0 flush。也就是说: 缓存的全部价值来自"正文重复"。
    生产上每个请求一份新正文, 那 23.7ms 那一档就是你的上限, 预算再大也不会更快。
    进一步验证: 拿 1657 条真记录连续扫, 每 KB 新建状态数从 84.7 掉到 16.2 后就 **不再收敛**,
    真实文本会一直要新状态。
    ⇒ 实践含义:
       · 把预算调到 0 flush, 拿到的是"别掉进悬崖"(必须做), 不是"变快 100 倍"。
       · 想再快, 只能让**表本身**少造状态 (§3/§4), 或者少扫正文 (前置粗筛)。

1.5 别用错的 benchmark
    🔴 同一份正文扫 N 遍的 benchmark **量不到任何东西**: 第一遍之后缓存全热, 换什么预算吞吐都一样。
    要量必须【轮换多份互不相同的真正文】, 而且看 flush 次数 / 新建状态数, 不能只看吞吐。


================================================================================
二、怎么量 (三个读数, 按粒度从粗到细)
================================================================================
2.1 进程级: DFAStats() / DFAStatsZero()
    挂在 re2 全局钩子上, 回答"这个进程里有人在 thrash"。归不了因 (一个进程几十个 Set 分不开),
    但零成本、随时能读。适合放在监控里当报警指标。
        hgmLibre2.DFAStatsZero()
        ...跑一批真正文...
        st := hgmLibre2.DFAStats()   // st.Resets == 0 才叫预算够

2.2 按 Set: set.MemInfo()
    回答"这一个 Set 现在什么水位、生涯清空过几次"。只读, 不会因为查询而建状态。
        mi := set.MemInfo()
        mi.StateBudget / mi.MemLeft   // 额度与剩余; Used() = 两者之差
        mi.States                     // 当前缓存里有多少个状态
        mi.ArenaCap                   // 实际占的内存 (远小于 StateBudget 说明"额度给多了也不花钱")
        mi.FlushesTotal               // 生涯整表清空次数 —— 这个是不是 0, 就是调预算的判据
        mi.StatesBuiltTotal           // 生涯建过多少状态 —— 这个才是"贵不贵"的直接指标
    🔴 标定预算的标准动作: 单线程, 先热身一遍, 然后扫一批【互不相同】的真正文, 看
       FlushesTotal 增量是不是 0。是 0 就够, 不是 0 就把 maxMem 翻倍重建再量。

2.3 按次调用: set.MatchStats(text, buf, &st)
    回答"**这一次**调用发生了什么"。st 在栈上, 不传就完全不统计 (热路径可以继续用 Match)。
        st.Flushes      本次扫描整表清空几次 (>0 = 这次调用有一段在两个数量级的慢速上跑)
        st.Grows        缓存长大几次 —— 【不丢状态】, 是好事, 别跟 Flushes 混
        st.StatesBuilt  本次新建几个状态 (稳态趋近 0; 一直不为 0 = 正文一直是新的)
        st.Bytes        本次正文字节数
        st.StatesEnd / st.StateBudget / st.MemLeft   扫完时的水位
    用法: Bytes/StatesBuilt 就是"每造一个状态摊到多少字节正文", 这个比值太小 (个位数) 说明
    这张表配这份语料本来就烧状态, 换多大预算都救不回来, 该动的是表 (§3)。
    ⚠ StatesBuilt 是 DFA 上累计计数器的前后差, 并发扫同一个 Set 会把别人建的算进来, 精确归因要单线程。

2.4 排障档: 谁在造状态 (要专门编译)
    默认构建里没有这套代码。排障时:
        CGO_CXXFLAGS="-O2 -DRE2_DFA_ATTRIB=1" go build ./...
        a := set.Attrib()
        for _, p := range a.Pats[:20] { ... }   // 已按 Excess 降序, p.Index 就是 patterns 的下标
    · a.Pats 是**每条 pattern 造状态的责任排行榜**。排序键是 Excess, 不是 States ——
      非锚定搜索下几乎每条 pattern 都出现在几乎每个状态里, States 会饱和成 100%, 没有分辨力。
    · a.NInstHist / a.NInstMax: 状态"宽度"分布 = 单个状态的造价。
    · a.BirthHist[64]: 正文等分 64 段, 每段造了多少状态。**平坦 = 全篇都在造**;
      集中在几个桶 = 有特定文本形态在触发, 去那几段看原文就知道是什么。
    · 环境变量 RE2_DFA_BIRTH_FILE=x.csv 可以把每个新建状态逐条落盘 (seq,off,len,ninst,owner),
      用来把"造状态的位置"精确对回正文原文。
    这个榜单是可信的, 有消融验证: 按榜单摘掉前 20 条 → 状态数降 5.4 倍; 随机摘 20 条 → 只降 1.4 倍。
    而且**跨语料稳定**: 三份形态完全不同的语料, 前 12 名有 10~11 名是同一批 pattern。
    ⇒ 拿手头任意一份真语料标定一次榜单就够, 不必每换一批语料重标。


================================================================================
三、状态爆炸的病根 (量出来的, 不是推的)
================================================================================
3.1 主项: 容差窗口的宽度, 而且基本线性
    把全表所有 `{0,N}` 收窄到 `{0,K}` (只是为了量, 不是能上线的改法):
        原样(≤200): 51844 个状态      {0,32}: 24218      {0,8}: 8678      {0,2}: 4366
    ⇒ **11.9 倍**, 每加 1 格窗口约 +700 个状态, 2~200 之间基本线性。
    原理: 自动机没有"我走到第几个字了"这种廉价手段, `X{0,W}Y` 只能在状态里展开成 W 份拷贝。

3.2 按形状切: 有没有间隙决定一切
        84 条【含 {0,N} 间隙】的 → 39842 个状态 (76.8%)
       139 条【不含间隙】的     →  1752 个状态 ( 3.4%)
    ⇒ 六成的 pattern 是白送的, 钱全花在那 84 条上。

3.3 次项: 组合确实超可加, 但只有 1.25~1.59 倍
        31 条宽窗口 + 192 条其余, 各自跑合计 32573, 并成一张 51844 → 1.59×
        112 条 + 111 条 两张表     各自跑合计 38552, 并成一张 51844 → 1.34×
    ⇒ "条数一多就是乘积级爆炸"这个说法**不准**。条数是次要项, **窗口宽度才是主项**。
      排优先级: **先削窗口, 再谈拆表。**

3.4 不是病根的东西 (试过, 不成立 —— 省得你再走一遍)
    · **正文的熵/随机性**: 随机全字节噪声造不出 thrash。它从来不走进任何窗口。
    · **压缩/混淆过的文本**: 反直觉但确凿 —— jquery.min.js 是所有语料里 **最便宜** 的一份。
      等体量对照: 真语料 82KB → 3906 个状态, jquery 87KB → **947** 个 (便宜 4.1 倍);
      整份 2.70MB 压缩 JS 只造 6412 个状态 (0-flush 门槛 ≤8MB), 同体量真语料造 51844 个 (门槛 64MB)。
      原因: 那些被压缩器改过名的标识符 (e/t/n/i...) 不含任何触发词, DFA 一直待在起始状态附近。
      逐段看更清楚: jquery 里造状态最多的四段, **全是这份文件里仅有的自然英文** ——
      版权注释、异常提示串、MIME 类型串、没被混淆的属性名。
    · **共享长公共前缀的几百条 pattern**: 公共前缀在 DFA 里就是一条路径, 区分度全在尾巴上,
      状态数反而很少。
    ⇒ 统一的规律: **驱动状态爆炸的是"正文有多频繁地走进容差窗口", 不是"字节看着有多乱"。**

3.5 一个要小心的例外: 字符类驱动的分支
    唯一一条"压缩 JS 比真语料还贵"的 pattern, 里面混着 `(?-i:\([A-Z]{2,5}\))` 这类
    **纯字符类分支** (而不是字面量), 而压缩 JS 满屏都是短大写标识符和括号 ⇒ 它天天在开窗口。
    ⇒ 通则: **由字符类而不是字面量驱动的分支, 代价随语料的字母表走, 会在你没预料到的语料上炸。**
      而且这跟"可过滤性差"是同一个毛病的两个面 —— 一条 pattern 如果没有像样的字面量锚点,
      它既躲不掉预筛, 又对语料形态极度敏感。**写规则时给每个分支留一个真实的字面量锚点。**

3.6 "让单个状态别那么贵" 这条路走不通 (已经量过了, 别再试)
    状态"宽度"(同时悬着多少条 NFA 线程) 就是单个状态的造价。把窗口从 ≤200 收到 {0,2}:
        状态数 51844 → 4366 (降 11.9 倍), 而平均宽度只从 37.3 → 35.7 (**降 4%**), 直方图形状几乎不动。
    ⇒ **窗口宽度控制状态的【数量】, 完全不控制【单价】。** 想降单价只能换 pattern 集本身。
    另外: 宽度也**不是条数的函数** —— 同样 111/112 条的两张表, 平均宽度差 3.3 倍。


================================================================================
四、调优动作清单 (按 收益/成本 排)
================================================================================
第 0 步 · 先量 (§2)。没有 FlushesTotal / StatesBuiltTotal 的数就不要动手。

A. **把预算调到 0 flush** —— 必做, 最便宜。
   翻倍法: 8→16→32→64MB, 每档单线程扫一批互不相同的真正文, 看 FlushesTotal 增量。
   代价基本是零: 额度给多了也不占物理内存 (状态区按需增长, 用不到的页根本不进 RSS),
   MemInfo().ArenaCap 就是实际花掉的内存, 可以直接对着看。
   ⚠ 别卡在"刚好够"那一档 —— 语料一变就掉下去。留一档余量。

B. **削窗口** —— 收益最大 (最高 11.9 倍), 但要改规则, 得判据方说了算。
   做法: 把 `A[^。\n]{0,80}B` 这类的 N 往小了调, 或者换成"同句/同段内共现"这种更强的约束。
   每削一档就跑一次 §2 的量, 曲线基本是线性的, 很好定价。

C. **按归因榜单定位病灶** —— 用 §2.4 的 Attrib 排行榜。
   前 20 条通常就吃掉一半以上的代价。拿到 Index 之后有三种处置:
     ① 改写这几条 (削窗口 / 加字面量锚点);
     ② 把这几条单独拎成一片 (见 D);
     ③ 确认它们的业务价值 —— 有时候最贵的那几条召回也最低, 直接下掉最划算。
   🔴 榜单是【定位】工具, 不是【上线】工具。摘掉 20 条状态降 5.4 倍, 但判据面也变了
     (命中数会掉), 不能拿消融结果当上线方案。

D. **拆片** —— 见 §5, 只在你知道该怎么切的时候做。

E. **前置粗筛** —— §1.4 说了生产上限就是"每份新正文都要造状态"。真要再快,
   只能是"少扫正文": 先用一道极便宜的门 (字面量 memmem / 小表 Set / 长度和类型过滤) 挡掉大多数正文,
   剩下的才进大表。这是唯一能抬上限的方向, 但它在调用方这边, 不在库这边。


================================================================================
五、拆片: 切法决定它是赚是亏 (本篇最反直觉的一条)
================================================================================
同一张 223 条表, 不同切法 (多片按串行多扫几遍算等效吞吐 = 1/Σ(1/各片)):

    方案                             片数  各片状态和  最大片状态  等效吞吐    最大片 0-flush 门槛
    整表 (不分)                        1     51844     51844     227.9 MB/s   64MB
    **按形状: 31 条宽窗口 / 192 条其余** 2     32573     18787   **229.9 MB/s**  **16MB**
    按来源分两张表                      2     38552     33008     224.2 MB/s   32MB
    按有无间隙: 84 / 139                2     41594     39842     176.4 MB/s   64MB
    按下标轮转 k=4                      4     49501     20086     133.6 MB/s   —
    按下标轮转 k=8                      8     44573     16229    ** 76.5 MB/s**  16MB

三条读法:
 1. **拆片几乎不减少总状态数** (51844 → 44573, 只降 14%), 它减少的是**单片工作集**
    (51844 → 16229, 降 3.2 倍)。而预算是按**最大片**给的, 不是按总数 ⇒ 这就是拆片值钱的全部原因。
 2. **随机/轮转切是纯亏**: k=8 每片都能跑到 600+ MB/s, 但要扫 8 遍, 等效只有 76.5 —— 比不拆慢 3 倍。
    "拆到不 flush 为止"这个停止条件会径直走到这里。**不要按下标随便分。**
 3. **按形状切是白赚**: 把 31 条宽窗口隔离出来, 等效吞吐持平略赢, 门槛 64MB → 16MB。
    赢在剩下 192 条那片能跑 553 MB/s, 一片极快弥补了多扫一遍。
    对比"84/139"那一刀: 病灶没被切细, 84 条那片仍然只有 266 MB/s, 于是净亏。

⇒ **拆片的可行性完全押在"能不能识别病灶条"上。** 先用 §2.4 的榜单看清楚, 再决定怎么切。
   另外注意: 直接取榜单前 K 名 **不等于最优二分** (实测门槛只从 64MB 降到 32MB, 输给手工按形状切的 16MB) ——
   两片切的目标是"让两片都小", 是个平衡问题, 榜单只是它的必需输入。


================================================================================
六、明确不用做的 / 已经排除的
================================================================================
· **不要为了省内存去卡预算**。悬崖是二值的, 省下来的几十 MB 换来的可能是 100 倍的慢。
· **不要用"同一份正文扫 N 遍"的 benchmark 下结论** (§1.5)。
· **不要指望缓存能救新正文** (§1.4)。缓存只对重复正文有用。
· **不要按"文本看起来乱不乱"来预判代价** (§3.4)。压缩 JS、随机噪声都是便宜的。
· **不要用一份语料的绝对状态数去推另一份语料** —— 换语料能差 4~8 倍。
  可以移植的是**排行榜的顺序**, 不是绝对值 (§2.4)。
· **不要指望改缓存淘汰策略**。已经离线模拟过: 最好的策略 (LRU / 只换热的一半) 比现在的整表清空
  只省 8~11%, 而下界 (新正文自己要的那些状态) 谁也省不掉。
· **静态打分器**: 纯静态地扫 pattern 里的 `{0,W}` 打分, 能把病灶排到前面, 但预测不了绝对状态数
  (离散度 2.3 倍), 因为绝对值跟语料强耦合。定位是 CI 体检 / code review 的排序工具,
  真实标定必须跑真语料。

七、一页速查
================================================================================
症状 → 动作:
  编译报 "set compile failed (out of memory)"   → NewRegexpSetMaxMem 翻倍预算, 别拆表
  吞吐忽高忽低 / 偶发超时                        → 量 MemInfo().FlushesTotal, >0 就翻倍预算 (§4A)
  预算已经 0 flush 但还是慢                      → 你在 §1.4 那个上限上。看 Attrib 榜单 (§2.4) 或前置粗筛 (§4E)
  想知道钱花在哪几条 pattern 上                  → -DRE2_DFA_ATTRIB=1 编译, set.Attrib().Pats[:20]
  想知道正文哪一段在烧状态                       → 同上, 看 a.BirthHist / RE2_DFA_BIRTH_FILE
  换了新语料就变慢                               → 找字符类驱动的分支 (§3.5), 那种 pattern 对语料形态最敏感
  要拆片                                        → 先看榜单再切, 绝对不要按下标轮转 (§5)

一句话总纲:
  **预算要给够 (二值, 别抠); 真正的成本在容差窗口的宽度; 缓存救不了新正文; 拆片必须按病灶切。**
