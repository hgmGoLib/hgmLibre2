hgmLibre2 性能优化经验 —— 给【调用者】看的
================================================================================
这份文件写给"手里有一批正则 (一条或几百条), 要用它一遍扫完正文"的人 (或 AI)。
只讲【调用方能做什么、该量什么数、改哪里有用】, 不讲库内部怎么实现的。

配套阅读: 同目录 状态数为什么会相乘.txt —— 那篇只讲一件事 (为什么几条 pattern 合成一张表
之后代价是乘的), 本篇讲"量什么、调什么"。两篇的结论互相引用。

数字来源有两类, 文中逐处标了:
  · 【真表】一张 223 条 / 一张 65 条的真规则表 + MB 级真语料, 换你自己的表和语料绝对值一定不同,
    但每一条【结论的方向】都在多份语料上复现过。
  · 【库测试】本仓库 reverse_test.go / maxmem_test.go / regexpset_test.go 里钉着的合成用例, 你 go test -v 就能自己跑出来。


================================================================================
零、先看这四句
================================================================================
1. 慢不慢, 只取决于一件事: **DFA 要不要现造状态**。造状态比走缓存慢两个数量级。
   flush (缓存被整表清空) 只是"造状态"的一个诱因, 它本身只贵 1.3~2.8 倍, 不是主因。
2. 调优只有三个旋钮, 按收益排: **方向 > 表的形状 > 内存预算**。
   · 方向 —— 同一条语言反着读, 状态数能从指数塌回线性 (实测 35149 → 45), **命中集一个字节不变**。
   · 形状 —— 改 pattern, 收益同量级, 但要判据方点头, 而且多半会动语义。
   · 预算 —— 只负责"别掉进 flush 悬崖", 它一个状态都不会少造。是止血, 不是治疗。
3. 造状态多不多, 主要取决于 **pattern 里"能当匹配起点的位置有多密"**, 跟"正文看起来有多乱/熵多高"
   完全无关 (随机噪声、压缩过的 JS 都是最便宜的语料)。
4. 调优的第一步永远是 **量, 不是猜**。库提供了四个读数 (§2), 五分钟就能知道你在哪一档。


================================================================================
一、心智模型: 三个旋钮 + 一道悬崖
================================================================================
1.1 maxMem 是一个旋钮, 同时抬两条完全不同的天花板
    单条: CompileMaxMem(pat, maxMem) / re.GetMaxMem()      集合: NewRegexpSetMaxMem(pats, maxMem)
    默认都是 DefaultMaxMem = 8MB (RE2::Options::kDefaultMaxMem), 传 <=0 回落到它。
    · 【编译期】程序 (NFA 指令) 条数上限。撞了 = 构造函数直接返回 error
      ("pattern too large - compile failed" / "set compile failed (out of memory)")。
      这是唯一会报错的地方。
    · 【运行期】剩下的额度给 DFA 状态缓存 (单条 Regexp 的额度还要在正向 prog 与反向 prog 之间
      按 2:1 分)。撞了 **不报错**: 缓存整表清空重来, 结果照样正确, 只是变慢。API 上收不到任何信号。
    ⇒ "能编过" ≠ "预算够"。前者只清了第一条天花板。

1.2 编译期撞墙时: 不要把表拆成两个 Set
    两个 Set = 正文扫两遍, 比多给几十 MB 内存贵得多。做法是把预算翻倍 (8 → 16 → 32 → 64MB)
    直到编过。构建期一次性开销, 之后 Set 只读、并发安全。
    ⚠ 这条只管编译期。如果表是在运行期真的 thrash (§2 量到 Flushes>0), 拆片反而可能更快 —— 见 §5。

1.3 运行期的悬崖长什么样
    【真表 223 条】同一批正文, 只改预算:
        预算 64MB → 0 次 flush → 291 MB/s
        预算 32MB → 每轮几次 flush → 2.6 MB/s
    差 113 倍。中间没有过渡带 —— 差一点点预算就整个掉下去。所以它是【够/不够】的二值问题,
    不是"多给点内存快一点"的连续问题。**不要试图给"刚好够"的预算, 要给"确定够"的预算。**
    【库测试】单条 `[A-Za-z][A-Za-z0-9]{2,19}key` 扫 60 份 16KB 互不相同的正文:
        预算 8MB(默认) → 6 次 reset      预算 256MB → 0 次      反着扫(默认 8MB) → 0 次 (状态峰值 9)
    ⇒ 同一条 pattern, 换方向比换 32 倍预算还管用, 而且不花内存。

1.4 但缓存救不了新正文 —— 这条最容易被忽略
    【真表】在完全不 flush 的 64MB 档:
        第 1 轮 (全新语料) 每份 80KB 正文 23.7ms
        第 2 轮 (同一批正文重扫, 一个状态都不新建) 每份 0.36ms
    **66 倍**, 而且全程 0 flush。也就是说: 缓存的全部价值来自"正文重复"。
    生产上每个请求一份新正文, 那 23.7ms 那一档就是你的上限, 预算再大也不会更快。
    进一步验证: 拿 1657 条真记录连续扫, 每 KB 新建状态数从 84.7 掉到 16.2 后就 **不再收敛**,
    真实文本会一直要新状态。
    ⇒ 实践含义:
       · 把预算调到 0 flush, 拿到的是"别掉进悬崖"(必须做), 不是"变快 100 倍"。
       · 想再快, 只能让**表本身**少造状态 —— 翻方向 (§4A) / 改 pattern (§4D), 或者少扫正文 (§4G)。

1.5 别用错的 benchmark
    🔴 同一份正文扫 N 遍的 benchmark **量不到任何东西**: 第一遍之后缓存全热, 换什么预算吞吐都一样。
    要量必须【轮换多份互不相同的真正文】, 而且看 flush 次数 / 新建状态数, 不能只看吞吐。
    🔴 语料还必须是【真的】。压缩 JS、随机字节这些"看起来很乱"的语料是**最便宜**的 (§3.5),
    拿它们标定出来的预算在真语料上会直接崩。


================================================================================
二、怎么量 (四个读数, 按粒度从粗到细)
================================================================================
2.1 进程级: GetDFAStats() / ResetDFAStats()
    挂在 re2 全局钩子上, 回答"这个进程里有人在 thrash"。归不了因 (一个进程几十个 Set 分不开),
    但零成本、随时能读。适合放在监控里当报警指标, 也是**单条 Regexp 正向路径唯一的读数**
    (单条没有 GetMemInfo)。
        hgmLibre2.ResetDFAStats()
        ...跑一批真正文...
        st := hgmLibre2.GetDFAStats()   // st.Resets == 0 才叫预算够
    字段: Resets (整表清空次数) · SearchFailures (DFA 放弃, 退回 NFA, 慢一个量级但结果仍对) ·
          LastStateBudget / LastCacheStates (最近一次清空时的额度与状态数 = working set 的下界样本)。

2.2 按 Set: set.GetMemInfo()
    回答"这一个 Set 现在什么水位、生涯清空过几次"。只读, 不会因为查询而建状态。
        mi := set.GetMemInfo()
        mi.StateBudget / mi.MemLeft   // 额度与剩余; GetUsedBytes() = 两者之差
        mi.States                     // 当前缓存里有多少个状态
        mi.ArenaCap                   // 实际占的内存 (远小于 StateBudget 说明"额度给多了也不花钱")
        mi.FlushesTotal               // 生涯整表清空次数 —— 这个是不是 0, 就是调预算的判据
        mi.StatesBuiltTotal           // 生涯建过多少状态 —— 这个才是"贵不贵"的直接指标
    🔴 标定预算的标准动作: 单线程, 先热身一遍, 然后扫一批【互不相同】的真正文, 看
       FlushesTotal 增量是不是 0。是 0 就够, 不是 0 就把 maxMem 翻倍重建再量。

2.3 按次调用: set.MatchStats(text, buf, &st) / rr.MatchStats(text, &st)  (rr 是 *RegexpReverse)
    回答"**这一次**调用发生了什么"。st (ScanStats) 在栈上, 不传就完全不统计
    (热路径可以继续用 set.Match / rr.MatchString, 零开销)。
        st.Flushes      本次扫描整表清空几次 (>0 = 这次调用有一段在两个数量级的慢速上跑)
        st.Grows        缓存长大几次 —— 【不丢状态】, 是好事, 别跟 Flushes 混
        st.StatesBuilt  本次新建几个状态 (稳态趋近 0; 一直不为 0 = 正文一直是新的)
        st.Bytes        本次正文字节数
        st.StatesEnd / st.StateBudget / st.MemLeft   扫完时的水位
        st.FellBack     只有 (*RegexpReverse).MatchStats 会置 true —— 反向 DFA 这次没跑成, 结果是退回
                        正向算的 (答案仍对, 但这次没省到状态)。见 §4A 末尾。
    用法: Bytes/StatesBuilt 就是"每造一个状态摊到多少字节正文", 这个比值太小 (个位数) 说明
    这张表配这份语料本来就烧状态, 换多大预算都救不回来, 该动的是方向或表 (§4A/§4D)。
    ⚠ StatesBuilt 是 DFA 上累计计数器的前后差, 并发扫同一个 Set 会把别人建的算进来, 精确归因要单线程。

2.4 排障档: 谁在造状态 (要专门编译)
    默认构建里没有这套代码。排障时:
        CGO_CXXFLAGS="-O2 -DRE2_DFA_ATTRIB=1" go build ./...
        a := set.GetAttrib()
        for _, p := range a.Pats[:20] { ... }   // 已按 Excess 降序, p.Index 就是 patterns 的下标
    · a.Pats 是**每条 pattern 造状态的责任排行榜**。排序键是 Excess, 不是 States ——
      非锚定搜索下几乎每条 pattern 都出现在几乎每个状态里, States 会饱和成 100%, 没有分辨力。
    · a.NInstHist / a.NInstMax: 状态"宽度"分布 = 单个状态的造价。
    · a.BirthHist[64]: 正文等分 64 段, 每段造了多少状态。**平坦 = 全篇都在造**;
      集中在几个桶 = 有特定文本形态在触发, 去那几段看原文就知道是什么。
    · 环境变量 RE2_DFA_BIRTH_FILE=x.csv 可以把每个新建状态逐条落盘 (seq,off,len,ninst,owner),
      用来把"造状态的位置"精确对回正文原文。
    这个榜单可信, 有消融验证: 按榜单摘掉前 20 条 → 状态数降 5.4 倍; 随机摘 20 条 → 只降 1.4 倍。
    而且**跨语料稳定**: 三份形态完全不同的语料, 前 12 名有 10~11 名是同一批 pattern。
    🔴 但它是【归因】不是【因果】, 而且这两者实测会**排出不同的顺序**: 在一张 65 条的真表上,
      GetAttrib 榜首那条的因果贡献只排第 2, 而因果第 1 名 (一条摘掉就省 88% 额度) 在 GetAttrib 榜上排第 3。
      原因见 §3.1 —— Excess 数的是状态的【单价】, 而额度是按状态的【数量】收的。
      ⇒ GetAttrib 用来**快速缩小范围** (一遍就出), 定死病灶要用**留一消融** (N 条跑 N+1 遍, 见 §2.5)。

2.5 因果版: 留一消融
    逐条摘掉再量全表, 差值 = 这条的真实成本。慢 (N+1 遍) 但这是唯一能读出因果的方法。
    🔴 摘的时候要按 **pattern 内容**摘, 不能按下标摘: 实测真表里有同一条 pattern 进了两次
      (只差一个 `\b`), 只摘一份的话另一份会把状态托住, 消融结果直接读错。
      **同一条 pattern 在同一张 Set 里进两次, 状态代价不是白进的。**


================================================================================
三、状态爆炸的病根 (量出来的, 不是推的)
================================================================================
3.1 主项: "谁能当匹配起点"。这决定状态的【数量】, 也就是钱
    非锚定搜索下, DFA 的一个状态 = 「窗口里还悬着哪些起点、各自走到第几步」。对 `S B{m,n} LIT`:
      · **S = B** (如 `[A-Za-z0-9][A-Za-z0-9]{2,19}key`): 每个字节都开一个新起点, 于是"还活着的
        起点"永远是【最近 k 个偏移】这一整段连续后缀 —— 只有 k+1 种可能 ⇒ **k+1 个状态**。
      · **S ⊊ B** (如 `[A-Za-z][A-Za-z0-9]{2,19}key`): 只有字母位置能开起点, 数字位置不能。
        于是存活集合是"最近 k 个偏移里, 哪几个当时是字母" —— 一个**任意子集** ⇒ 最坏 **2^k**。
    实测同一条语言、同一份语料, 只把首字符从"必须是字母"放宽成"字母或数字":
        [A-Za-z][A-Za-z0-9]{2,19}key      57771 状态 · 8.00MB · 253 MB/s
        [A-Za-z0-9][A-Za-z0-9]{2,19}key      55 状态 · 0.06MB · 701 MB/s   ← 放宽首字符 (超集方向)
        \b[A-Za-z][A-Za-z0-9]{2,19}key       59 状态 · 0.06MB · 689 MB/s   ← 词首守卫 (收窄方向)
        [A-Za-z][A-Za-z0-9]{2,}key           10 状态 · 0.06MB · 668 MB/s   ← 去掉上界 (超集方向)
    ⇒ **1050 倍, 而计数的界一个字都没动。** 引爆的不是"重复有多长", 是"谁能开起点"。
      `\b` / 字面前缀 / 反着扫 (§4A) 全都是同一个机制的不同触发方式: 让起点变稀疏。

3.2 次项: 计数长度 × 类字宽 买的是状态的【单价】, 不是数量
    把窗口从 ≤200 收到 {0,2} (真表 223 条):
        状态数 51844 → 4366 (降 11.9 倍), 而平均状态宽度只从 37.3 → 35.7 (**降 4%**), 直方图形状几乎不动。
    另一条对照 (合成): `[A-Za-z0-9]{52}LIT[A-Za-z0-9]{28}` 收成 {4}/{4} 之后每状态从 220B → 122B,
    而状态数 56 → 8 (本来就没几个)。
    ⇒ **想省钱先看数量 (§3.1), 单价那一面顶多值几倍。** "让单个状态别那么贵"这条路已经量过, 走不通。
      另外: 宽度也**不是条数的函数** —— 同样 111/112 条的两张表, 平均宽度差 3.3 倍。

3.3 窗口宽度: 真表上是线性的, 是可定价的旋钮
    把全表所有 `{0,N}` 收窄到 `{0,K}` (只是为了量, 不是能上线的改法):
        原样(≤200): 51844 个状态      {0,32}: 24218      {0,8}: 8678      {0,2}: 4366
    ⇒ **11.9 倍**, 每加 1 格窗口约 +700 个状态, 2~200 之间基本线性。
    按形状切开看, 钱花在哪一目了然:
         84 条【含 {0,N} 间隙】的 → 39842 个状态 (76.8%)
        139 条【不含间隙】的     →  1752 个状态 ( 3.4%)
    ⇒ 六成的 pattern 是白送的。

3.4 条数是次要项: 组合确实超可加, 但只有 1.25~1.59 倍
        31 条宽窗口 + 192 条其余, 各自跑合计 32573, 并成一张 51844 → 1.59×
        112 条 + 111 条 两张表     各自跑合计 38552, 并成一张 51844 → 1.34×
    (合成的三条极端 pattern 上超可加到过 2.98×, 但那是刻意挑的。)
    ⇒ "条数一多就是乘积级爆炸"这个说法**不准**。排优先级: **先治病灶条, 再谈拆表。**
      为什么是乘法、以及"一条 pattern 的代价只在它所在的表里成立", 见 状态数为什么会相乘.txt。

3.5 不是病根的东西 (试过, 不成立 —— 省得你再走一遍)
    · **正文的熵/随机性**: 随机全字节噪声造不出 thrash。它从来不走进任何窗口。
    · **压缩/混淆过的文本**: 反直觉但确凿 —— jquery.min.js 是所有语料里 **最便宜** 的一份。
      等体量对照: 真语料 82KB → 3906 个状态, jquery 87KB → **947** 个 (便宜 4.1 倍);
      整份 2.70MB 压缩 JS 只造 6412 个状态 (0-flush 门槛 ≤8MB), 同体量真语料造 51844 个 (门槛 64MB)。
      原因: 那些被压缩器改过名的标识符 (e/t/n/i...) 不含任何触发词, DFA 一直待在起始状态附近。
      逐段看更清楚: jquery 里造状态最多的四段, **全是这份文件里仅有的自然英文** ——
      版权注释、异常提示串、MIME 类型串、没被混淆的属性名。
    · **共享长公共前缀的几百条 pattern**: 公共前缀在 DFA 里就是一条路径, 区分度全在尾巴上,
      状态数反而很少。
    ⇒ 统一的规律: **驱动状态爆炸的是"正文有多频繁地把某条 pattern 的分支续下去", 不是"字节看着有多乱"。**

3.6 一个要小心的例外: 字符类驱动的分支
    唯一一条"压缩 JS 比真语料还贵"的 pattern, 里面混着 `(?-i:\([A-Z]{2,5}\))` 这类
    **纯字符类分支** (而不是字面量), 而压缩 JS 满屏都是短大写标识符和括号 ⇒ 它天天在开窗口。
    ⇒ 通则: **由字符类而不是字面量驱动的分支, 代价随语料的字母表走, 会在你没预料到的语料上炸。**
      而且这跟"可过滤性差"是同一个毛病的两个面 —— 一条 pattern 如果没有像样的字面量锚点,
      它既躲不掉预筛, 又对语料形态极度敏感。**写规则时给每个分支留一个真实的字面量锚点。**


================================================================================
四、调优动作清单 (按 收益/成本 排)
================================================================================
第 0 步 · 先量 (§2)。没有 FlushesTotal / StatesBuiltTotal 的数就不要动手。
A、B 两条【不改语义、不改 pattern】, 只是把问题问小一点, 应该先试。

A. 🥇 **翻方向: 反着扫** —— 收益最大, 而且是唯一【不改语义】的一招。
   API:  单条  rr, _ := CompileReverse(pat) (或 CompileReverseMaxMem / MustCompileReverse)
               → rr.MatchString(s) / rr.Match(b) / rr.MatchStats(s, &st)
               —— 反向是【单独一个类型 RegexpReverse】, 不是 Regexp 上的方法: 两个方向是两套程序、
                  两份 DFA 缓存, 一条 pattern 通常只走一个方向, 要两个方向就编两个对象。
         集合  NewRegexpSetReverseMaxMem(pats, maxMem) · set.Reverse()
               —— 反向 set 只有这一个构造函数 (会想反着扫的表通常就是正向撞过预算的那张,
                  建的时候顺手把预算定了; 要默认 8MB 就传 DefaultSetMaxMem)。
   为什么有效: §3.1 那个 2^k 完全来自"同时悬着哪些起点"。这一族 pattern 的必需字面量在**尾巴上**
   (`…key`), 正着扫每个偏移都是潜在起点; 反过来读, 那个字面量变成**首部**守卫, 起点退化成
   "文本里出现过几次这个字面" ⇒ 位集根本长不起来。这是条定理不是巧合: `(a|b)*a(a|b)^k` 需要
   2^k 个 DFA 状态, 它的反语言 `(a|b)^k a(a|b)*` 只要 k+2 个。
   【库测试 · 单条一张 set · 120 份 8KB 语料】
       [A-Za-z][A-Za-z0-9]{2,19}key    正向 35149 状态 · 5.35MB      反向 45 状态 · 0.01MB
                                       命中集一致 (16 == 16)
   【真表 65 条 · 6.21MB 真语料 · 只把 1 条翻向, 其余 64 条不动】
       单趟全表  27949 状态 · 23.52MB ·  96 MB/s
       两趟合计   4701 状态 ·  3.06MB · 186 MB/s (有效吞吐, 已经算上文本要过两遍) · 2285 处命中逐条不变
   🔴 三条使用要点:
    1. **方向是【每条 pattern 各自】的决定, 不是全局开关。** 镜像的一对 (库测试钉着):
         `(?s).{20}key`  正向 21 状态 / 反向 1        `key(?s).{20}`  正向 1 / 反向 21
       没样本时看形状: 必需字面量靠尾巴 ⇒ 该翻; 靠头 ⇒ 别翻。有样本时逐条量两个方向取小的。
       ⇒ 实践做法是**建两张 Set (一正一反), 各扫一趟**, 而不是整表翻。见 §5。
    2. **要位置就用Re2Set_rrl_t** (2026-08-27 之前这里写的是"反向只回答命中没命中")。
       `RegexpSetReverse.NewRe2Set_rrl()` 一遍扫就直接给不重叠的命中区间 —— 反向搜索天然
       知道匹配的【左端】, 而 leftmost/rightmost-longest 这个口径本来就定义在起点上, 所以
       补右端只是一次锚定解析, 不用再扫一遍正文。
       ⚠ 口径是 **rightmost-longest**, 区间按 Lo **降序**来 —— 与正向那个是镜像, 不是同一个
         答案。两者只在"两个真匹配互相交叠"时才分家; 要跟 stdlib 的 re.Longest() 逐字节对上
         就得用正向那个。全文见 doc/fll的leftmost-longest保证.md 第 8 节。
       单条 RegexpReverse 那边仍然只回答"命中没有"(没有 Find, 也不打算有): 先用它当便宜的门,
       极少数命中的再走一次正向 FindStringIndex。
       命中集与正向逐位相同, 这是"同一条语言换个方向读", 不是近似, 不缩语义。
    3. **别自己反转 pattern 和正文。** 库走的是 RE2 编译器自带的反向程序 (concat 反序 / ^$ 对调 /
       多字节 rune 的字节序列反编 / \b 不变), 正文原封不动, 一个字节都不复制。
       它不只是更省事, 是**更省**: 同一条语言同一串字节, 库的反向 **17 个状态**, 手写文本反转
       **25247 个** (~1485×, reverse_test.go 的 TestReverseIsNotHandRolledTextReversal)。
       原因是 RE2 的 Simplify 把 `x{2,19}` 展开成"必需拷贝在前、可选嵌套在后", 编译器反序之后
       可选嵌套跑到了读取顺序的**前面**, 各起点的活跃集合互相嵌套而不构成任意子集。
       ⚠ 早期实验里"镜像 pattern 反着扫贵 1607 倍"那个数**只对手写反转成立**; 走这个 API 同一个
         镜像形状只贵二十几倍 (上面那对 21 / 1)。别拿旧数字吓自己。
   ⚠ 两条边角:
    · 单条 Regexp 的反向路径**一定走 DFA**, 不走 RE2 对短文本的 bitstate/onepass 快路径,
      所以小正文上它不一定比 MatchString 快。它换的是状态数, 不是常数。
    · 单条反向 DFA 有可能中途放弃 (RE2 的 bail 启发式), 那时库自动退回正向算, 答案仍然正确,
      ScanStats.FellBack 会置 true。**看到 FellBack 常年为 true 就说明这条没省到, 别指望它。**
      RegexpSet 不会走到这里 (RE2 对 kManyMatch 禁掉了 bail, 只 flush)。

B. **少问一点: 只要"有没有命中"就用 MatchAny** —— 改一行调用, 零风险, 命中的那几次白赚。
   API:  set.MatchAny(text) / set.MatchAnyBytes(b)  —— 【不传 buf】(它不回填 index)。
         (Match/MatchStats 那个 buf 该开多长, 用 set.GetPatternLen())
   为什么比 len(set.Match(text, buf)) > 0 快: Match 要回答"哪几条", DFA 必须走到正文末尾才知道
   命中集全不全; MatchAny 不取 index, 底下 RE2 就打开 want_earliest_match, **扫到第一个命中位置
   立刻收工**。命中越靠前、正文越长, 省得越多。
   【库测试 · 8MB 正文 · 命中落在第 0 字节】
       set.MatchAny(s)            2.12µs
       len(set.Match(s, buf)) > 0 11.18ms      (~5000×; regexpset_test.go 的
                                                TestRegexpSetMatchAny_EquivAndEarlyExit 钉着 ≥20×)
   ⚠ 三条边界 —— 别把它当解药:
    · 它省的是**扫多少字节**, 不是状态数。与 A 正交: 该造的状态一个不少, 只是不再一路造到末尾。
    · **不命中的正文仍然全扫一遍。** 生产上绝大多数正文是不命中的, 所以整体收益取决于你的命中率
      和命中位置分布, 不像 A 那样是稳定的几十倍。它是白捡, 不是治疗。
    · 走的是与 Match **同一份** DFA 状态缓存 (kManyMatch 那份), 多用这条快路径不会多占一份内存。
   ⇒ 判据很简单: 看调用点拿到 index 之后有没有真的用。只是 `len(...) > 0` 判个真假的, 就该换。
     真需要"哪几条"就老老实实用 Match —— 早退和"命中集完整"本来就不可兼得。

C. **把预算调到 0 flush** —— 必做, 最便宜。
   翻倍法: 8→16→32→64MB, 每档单线程扫一批互不相同的真正文, 看 FlushesTotal / GetDFAStats().Resets 增量。
   代价基本是零: 额度给多了也不占物理内存 (状态区按需增长, 用不到的页根本不进 RSS),
   GetMemInfo().ArenaCap 就是实际花掉的内存, 可以直接对着看。
   ⚠ 别卡在"刚好够"那一档 —— 语料一变就掉下去。留一档余量。
   ⚠ 这一步**一个状态都不会少造**。它买的是"别掉悬崖", 不是"变快"。真要省状态看 A / D。

D. **改 pattern** —— 收益与 A 同量级, 但要改判据, 而且会动语义。
   按性价比排:
     ① 给病灶分支加 `\b` 或一个字面前缀守卫 —— 一个字符收 4~1000 倍 (§3.1)。**是收窄, 会丢命中, 必须对拍。**
     ② `{m,n}` → `{m,}` 去掉上界 —— 也是千倍量级, 而且是**超集方向** (只多报不漏报), 比 ① 安全。
     ③ 把首字符类放宽到与重复类相同 —— 超集方向, 千倍量级 (§3.1 那张表)。
     ④ 削窗口: `A[^。\n]{0,80}B` 的 N 往小了调 —— 线性可定价, 最高 11.9 倍 (§3.3), 但也是收窄。
   ⇒ ②③ 是超集不用重新评审召回, 应该先试; ①④ 动了判据面, 得规则作者点头。

E. **按归因榜单定位病灶** —— 用 §2.4 的 GetAttrib 排行榜缩范围, 用 §2.5 的留一消融定死。
   前几条通常就吃掉一半以上的代价 (真表上一条占 88% 的额度)。拿到 Index 之后四种处置:
     ① 翻方向 (A);  ② 改写 (D);  ③ 单独拎成一片 (F);
     ④ 确认业务价值 —— 有时候最贵的那几条召回也最低, 直接下掉最划算。
   🔴 榜单是【定位】工具, 不是【上线】工具。摘掉 20 条状态降 5.4 倍, 但命中数也掉了,
     不能拿消融结果当上线方案。

F. **拆片 / 分泳道** —— 见 §5, 只在你知道该怎么切的时候做。

G. **前置粗筛** —— §1.4 说了生产上限就是"每份新正文都要造状态"。真要再抬上限,
   只能是"少扫正文": 先用一道极便宜的门 (字面量 memmem / Aho-Corasick / 小表 Set / 长度和类型过滤)
   挡掉大多数正文, 剩下的才进大表。这在调用方这边, 库不提供。
   实测过的两条经验:
    · **粗筛的必需字面量要叉乘着抽, 不能只挑最长的那个分支。** `(?:aa|bb)_(?:live|test|prod)_…`
      按"最长"会挑中 `live`/`test`/`prod` 这种满地都是的英文词; 叉乘成 `aa_live_`/`bb_test_` 之后
      复核字节直接减半。
    · 🔴 **粗筛的"对抗面"比纯 DFA 小得多。** 直觉上"正文塞满触发词就退化"是对的, 但实测把触发词按
      1/64 字节的密度塞进正文, 先垮的是**纯 DFA** (状态 2.5~7 倍地涨, 64MB 预算下掉到 4.3 MB/s),
      而预筛那条只是复核窗口多开几次, 从 167 掉到 82 MB/s —— **是斜坡不是悬崖** (最坏一档差 33 倍)。
      粗筛和反着扫 (A) 是**互补**的: 前者治"有稀有字面量"的大多数条, 后者治"字面量满地都是
      但起始类窄于重复类"的那几条。


================================================================================
五、拆片 / 分泳道: 切法决定它是赚是亏 (本篇最反直觉的一条)
================================================================================
5.1 按方向切 —— 唯一"白赚"的切法, 而且不动任何 pattern
    建两张 Set: 一张 NewRegexpSet (正向), 一张 NewRegexpSetReverseMaxMem (反向), 各扫一趟, 命中集求并。
    真表 65 条上只有 1 条值得翻, 就把总账从 27949 状态 / 23.52MB / 96 MB/s 打到
    4701 / 3.06MB / 186 MB/s (有效吞吐, 两趟都算进去了), **2285 处命中一处不差**。
    怎么分组: 逐条单跑两个方向 (各建一张单条 set, 量 GetMemInfo().States), 便宜 4 倍以上才翻。
    没样本时看形状 —— 必需字面量靠尾巴的翻, 靠头的不翻。

5.2 按代价形状切 —— 有效, 但要先认出病灶条
    【真表 223 条】不同切法 (多片按串行多扫几遍算等效吞吐 = 1/Σ(1/各片)):

    方案                             片数  各片状态和  最大片状态  等效吞吐    最大片 0-flush 门槛
    整表 (不分)                        1     51844     51844     227.9 MB/s   64MB
    **按形状: 31 条宽窗口 / 192 条其余** 2     32573     18787   **229.9 MB/s**  **16MB**
    按来源分两张表                      2     38552     33008     224.2 MB/s   32MB
    按有无间隙: 84 / 139                2     41594     39842     176.4 MB/s   64MB
    按下标轮转 k=4                      4     49501     20086     133.6 MB/s   —
    按下标轮转 k=8                      8     44573     16229    ** 76.5 MB/s**  16MB

    三条读法:
     1. **拆片几乎不减少总状态数** (51844 → 44573, 只降 14%), 它减少的是**单片工作集**
        (51844 → 16229, 降 3.2 倍)。而预算是按**最大片**给的, 不是按总数 ⇒ 这就是拆片值钱的全部原因。
     2. **随机/轮转切是纯亏**: k=8 每片都能跑到 600+ MB/s, 但要扫 8 遍, 等效只有 76.5 —— 比不拆慢 3 倍。
        "拆到不 flush 为止"这个停止条件会径直走到这里。**不要按下标随便分。**
     3. **按形状切是白赚**: 把 31 条宽窗口隔离出来, 等效吞吐持平略赢, 门槛 64MB → 16MB。
        赢在剩下 192 条那片能跑 553 MB/s, 一片极快弥补了多扫一遍。
        对比"84/139"那一刀: 病灶没被切细, 84 条那片仍然只有 266 MB/s, 于是净亏。

5.3 一条硬约束: **把 Set 拆散成"逐条扫"是自废武功**
    实测过一版"粗筛开门之后逐条复核"的方案: 常开的 6~8 条各扫一遍就等于正文过 6~8 遍,
    70 MB/s, **比什么都不做还慢**。**RegexpSet 的全部价值就是"一趟扫完 N 条"**,
    残余的那些条无论多少, 也必须是**一张 Set 一趟**。

⇒ **拆片的可行性完全押在"能不能识别病灶条"上。** 先用 §2.4 + §2.5 看清楚, 再决定怎么切。
  另外注意: 直接取归因榜单前 K 名 **不等于最优二分** (实测门槛只从 64MB 降到 32MB, 输给手工按形状切
  的 16MB) —— 两片切的目标是"让两片都小", 是个平衡问题, 榜单只是它的必需输入。


5.4 上面 §5.2 第 2 条"轮转切纯亏"有前提: 整表【没被状态卡住】 (2026-08-18 补测)
--------------------------------------------------------------------------------
上表那个 223 条表的基线是 227.9 MB/s —— 它本来就不在状态受限区, 于是多扫 8 遍的常数成本
主导一切, 轮转切当然亏。但同一件事在【深度状态受限】的表上完全反过来。

某调用方的 8 张生产规则表 × 10 个语料族 (含刻意构造的恶意输入) 重测, 同一张 106 条表上两个区段
同时出现 (K=8, 按下标轮转):

    语料族              整表基线      K=8      结论
    evilNearMiss      154 MB/s     71      0.46x  ← §5.2 那个区段, 亏
    benignProse        85          62      0.74x  亏
    evilClassBranch    25          46      1.85x
    evilUtf8Fold        3.9        21.6    5.59x
    evilHighEntropy     1.5        13.8    9.31x  ← 赚

**交叉点在 30~80 MB/s 之间。** 拆片是赚是亏不取决于切法, 取决于整表在【这份正文】上有没有
被状态卡住: 状态杠杆 vs (K-1) 遍额外扫描的常数成本, 谁大听谁的。所以 §5.2 第 2 条应读作
"**在整表已经跑到 200+ MB/s 的表上**, 轮转切纯亏", 而不是"轮转切一律纯亏"。

推论: 拆片是【逐表】决策, 不是全局开关。同一批表里 8 条那张 (基线 356 MB/s) 拆了就是纯亏
(0.77x), 而 106 条那张拆了赚 9 倍 —— 条数少的表根本没有组合爆炸可拆。


5.5 §5.1 的分组探针是客观可测的: 按【方向】切 vs 按下标切, 实测 (2026-08-18)
--------------------------------------------------------------------------------
§5.2 结尾说"可行性押在能不能识别病灶条", 但那里给的办法是人眼看形状。方向给了一个可以算出来的:
每条 pattern 各建一个单条正向 set 和单条反向 set, 同一批语料各扫一遍比累计 StatesBuilt,
小的那边就是它该去的组 (readme.txt 早就写了这个做法, 这里是把它用在整表上的实测)。

同一张 106 条表, 按【相同的正文扫描遍数】对比:

    正文扫几遍   按下标切(contig/rr 取好的)   按方向切 + 每侧再拆
       2                2.67x                  **4.27x**
       4                6.33x                  **7.67x**
       8                9.20x                  **10.0x**

方向在每个遍数上都赢, 2 遍那档赢得最多。原因不是"每片条数更少"(那是按下标切也有的),
而是把状态爆炸的那批【整体挪到它不爆炸的方向上】—— 那是多扫一遍换不来的量。
8 张表实测反向更省的条数占 5%~50%, 其中凭据类 (keyword + 宽值窗口, 即 key(?s).{20} 那一侧)
最典型; 反过来 \bATATT3[A-Za-z0-9_\-=]{186}\b 这种"定长字面量前缀 + 宽窗口在后"的
正向 2 状态 / 反向 1196 状态, 探针会正确地把它留在正向。

⚠ 代价照样要说: 天花板是降的。同表最快那格 154 → 71 MB/s (K=4)。整张表从 1.5~154
  (105 倍跨度) 收窄到 15~74 (5 倍)。要的是"任意输入不能太慢"就该做, 要的是"平均更快"就不该做。


5.6 选 K 必须带【上限约束】: 只按"最慢那一族"选, 会把便宜语料悄悄砸掉 (2026-08-19)
--------------------------------------------------------------------------------
§5.4/§5.5 的判据都是"最慢那一族有多慢"。照这个判据单独去选 K, 会选出一个在报表上看不出问题、
实际上把【便宜语料】拖垮的档次。实测:

    一份 16MB 全 'x' 的正文 (一条都不命中, 状态几乎为 0), 整条门链 8 张表:
        现状(每张一遍)          84.6 MB/s     0.19 秒
        每侧 4 片(每张 8 遍)     16.7 MB/s     0.96 秒   ← 5 倍的净亏, 而"最慢族"那一列毫无变化

机理很简单: 便宜语料没有状态可省, 拆片对它【只剩纯成本】—— 拆 N 片就老老实实慢 N 倍。
而它永远不会是"最慢那一族", 于是这笔账在最慢族这个判据下完全隐形。

修法两步, 缺一不可:
  ① 探针语料里必须有一族【长游程单调字节】(benignBulk: 200~600 字节的同一个字符 + 换行)。
     prose / minifiedJs / jsonApi 都不够 —— 它们还是会造一些状态, 掩盖这一档的斜率。
  ② 选 K 时加【上限约束】: 任何一族都不许比现状慢过 2 倍, 违反的档次直接否掉, 不参与选优。

加上之后同一批表选出来的 K 从 4 掉到 1~2 (即"只按方向切两片"为主), 最慢族的收益从
8.9x 降到 6.7x, 但便宜语料那一档的代价从 5 倍收回到 2 倍以内。这个交换是对的:
"任意输入不能太慢"是【双向】的 —— 抬底线不许以砸掉另一档为代价。


================================================================================
六、明确不用做的 / 已经排除的
================================================================================
· **不要为了省内存去卡预算**。悬崖是二值的, 省下来的几十 MB 换来的可能是 100 倍的慢。
· **不要用 `len(set.Match(...)) > 0` 当布尔门** (§4B)。只要真假就用 MatchAny —— 它命中即收工,
  而 Match 为了回答"哪几条"必须扫到正文末尾。
· **不要指望抬预算能省状态**。它一个状态都不会少造 (§4C), 是止血不是治疗。
· **不要用"同一份正文扫 N 遍"的 benchmark 下结论** (§1.5)。
· **不要指望缓存能救新正文** (§1.4)。缓存只对重复正文有用。
· **不要按"文本看起来乱不乱"来预判代价** (§3.5)。压缩 JS、随机噪声都是便宜的。
· **不要用一份语料的绝对状态数去推另一份语料** —— 换语料能差 4~8 倍 (合成的极端例子上差过 15000 倍)。
  可以移植的是**排行榜的顺序**, 不是绝对值 (§2.4)。
· **不要自己反转 pattern + 正文来实现"反着扫"** (§4A 要点 3)。既不省状态, 又会拆坏多字节 UTF-8,
  还要多复制一份正文。
· **不要整表翻方向**。方向是每条 pattern 各自的决定, 翻错了就是几十倍地贵 (§4A 要点 1)。
· **不要指望改缓存淘汰策略**。已经离线模拟过: 最好的策略 (LRU / 只换热的一半) 比现在的整表清空
  只省 8~11%, 而下界 (新正文自己要的那些状态) 谁也省不掉。
· **不要指望"让单个状态便宜点"** (§3.2)。钱全在数量上。
· **静态打分器**: 纯静态地扫 pattern 里的 `{0,W}` / `S ⊊ B` 打分, 能把病灶排到前面, 但预测不了
  绝对状态数 (离散度 2.3 倍), 因为绝对值跟语料强耦合。它是 CI 体检 / code review 的排序工具,
  真实标定必须跑真语料。
· **不要指望换个正则引擎**: 有界重复用"计数寄存器"而不是状态来做 (counting-set automata /
  Hyperscan 的 Castle) 确实能把这一族的内存从 MB 级打到几十字节, 但离线比价的结论是
  ——【健康的】DFA 全程 675~704 MB/s 且与界无关, 寄存器路线只赢"病了的那一档"。
  也就是说: **只要 pattern 不是那个坏形状, 现成的 DFA 就已经够好了。** 该做的是让形状变好 (A/C),
  不是换引擎。


================================================================================
七、一页速查
================================================================================
症状 → 动作:
  编译报 "compile failed (out of memory)"       → 预算翻倍 (CompileMaxMem / NewRegexpSetMaxMem), 别拆表
  吞吐忽高忽低 / 偶发超时                        → 量 FlushesTotal / GetDFAStats().Resets, >0 就翻倍预算 (§4C)
  预算已经 0 flush 但还是慢                      → 你在 §1.4 那个上限上。看 §4A 能不能翻方向, 或 §4E 找病灶
  某条 pattern 形如 `S B{m,n} LIT` 且 S ⊊ B     → 先试 CompileReverse / NewRegexpSetReverseMaxMem (§4A), 不改语义
  想知道钱花在哪几条 pattern 上                  → -DRE2_DFA_ATTRIB=1 编译看 GetAttrib().Pats, 再用留一消融定死 (§2.5)
  想知道正文哪一段在烧状态                       → 同上, 看 a.BirthHist / RE2_DFA_BIRTH_FILE
  换了新语料就变慢                               → 找字符类驱动的分支 (§3.6), 那种 pattern 对语料形态最敏感
  只想知道"有没有命中", 不要"哪几条"        → set.MatchAny / MatchAnyBytes (§4B), 命中即收工, 不用传 buf
  要拆片                                        → 先确认整表【真的被状态卡住】(§5.4), 再按方向切 (§5.1),
                                                  然后按形状切 (§5.2), 绝对不要按下标轮转
  单条 Regexp 想看水位                           → 单条没有 GetMemInfo; 用 (*RegexpReverse).MatchStats 的 ScanStats,
                                                  正向路径只能看进程级 GetDFAStats()

一句话总纲:
  **先看能不能翻方向 (不改语义, 收益最大); 病根是"谁能当起点"而不是"重复有多长";
    预算要给够但它不省状态; 缓存救不了新正文; 拆片必须按病灶切, 而且残余永远是一张 Set 一趟。**
