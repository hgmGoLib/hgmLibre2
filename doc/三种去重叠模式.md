# 一遍扫一张表, 拿到"每条 pattern 命中在哪": 三种去重叠模式怎么选

管的是 `Re2Set_fll_t` / `Re2Set_frel_t` / `Re2Set_rrl_t` 这三个类型 ——
**一张 N 条 pattern 的表, 扫正文一遍, 直接拿到"第几条 · 从哪到哪"**。

不管的:

- 单条正则怎么用 → `README.md` 的 Supported API;
- 表本身多大多贵 (状态数 / `maxMem` / flush) → `doc/set性能优化经验.txt`、`doc/状态数为什么会相乘.txt`;
- `fll` 那条 leftmost-longest 保证的长版证明与对拍口径 → `doc/fll的leftmost-longest保证.md`。

---

## 0. 先说清楚要解的是哪个问题

`RegexpSet.Match` 回答的是**"这 N 条里哪几条命中了"**, 【不给位置】。
要位置, 老写法是两段式:

```go
ids := set.Match(body, buf)          // 第 1 遍: 全文
for _, id := range ids {
    re[id].FindAllStringIndex(body, -1)   // 第 2..1+k 遍: 每条各一遍全文
}
```

命中 k 条 = **1+k 遍全文**, 而且后面那 k 遍走的是最贵的**非锚定**扫描
(`.*?` 前缀让每个位置都能当起点, 状态数对计数上界指数增长 —— 同一条 pattern 加个 `\b`
就是 967 倍的差距, 见 `doc/状态数为什么会相乘.txt`)。

可位置在第一遍里**本来就算出来过**: RE2 的 `kManyMatch` DFA 每走到一个"某条能在此结束"的
字节都记了一次, 扫完把它扔了。这三个类型就是把这一遍记下来的东西接出来 ——
6.4MB 正文上实测 `Match` 单独 18.5ms, `Match` + 收全部端点 18.4ms, **位置是白送的**。

🔴 但白送的是**端点集合**, 不是**匹配序列**。一遍扫描交出来的是"第 i 条的匹配端点落在
这些位置上", 里面:

- 没有起点终点的**配对** (`kManyMatch` 只报端点);
- 没有**优先级**信息 (RE2 的贪心活在 NFA 指令优先级里, `kManyMatch` 这一档把它丢了);
- 同一条 pattern 的匹配**互相重叠** (`aa|a` 撞 `"aaa"`: 端点 1/2/3 都是真的)。

所以"把端点集合收敛成一串互不重叠的区间"这一步是**必须做的选择**, 而且**不止一种做法**。
这一页讲的就是这三种做法。

🔴🔴 **`leftmost-longest` 只是其中一种, 不是"对的那种", 也不一定是你要的那种。**
它唯一的特殊之处是"能和 stdlib 的 `re.Longest().FindAllStringIndex` 逐字节对上",
仅此而已 —— 它既不是最快的, 在"别把命中截短"这件事上也不比另外两种强。
见 §4。

## 1. 速查表

| | `Re2Set_fll_t` | `Re2Set_frel_t` | `Re2Set_rrl_t` |
|---|---|---|---|
| 名字怎么读 | **f**orward + **l**eftmost-**l**ongest | **f**orward + **r**ightmost-**e**nd-**l**ongest | **r**everse + **r**ightmost-**l**ongest |
| 第一趟方向 | 正向 | 正向 | **反向** (从末尾往前) |
| 挂在谁身上 | `*RegexpSet` | `*RegexpSet` | `*RegexpSetReverse` |
| 锚哪个坐标 | 起点最靠左 | **终点**最靠右 | 起点最靠右 |
| 同锚点取 | 最长 | 最长 (= 起点最靠左) | 最长 |
| 输出顺序 (同一条内) | `Start` **升序** | `Start` **升序** | `Start` **降序** |
| 与 stdlib 对得上 | ✅ `re.Longest().FindAllStringIndex` 逐字节 | ❌ | ❌ |
| 补起点问几次锚定 | **每个右端**一次 | **每个分量**一次 | 每处命中一次 |
| 常驻额外内存 | 单条反向 set 缓存 (最大那张 158 条表实测 9.6MB) | 同左 | 同左 |
| 一句话适用面 | 要和标准库口径完全一致 | 命中密 / 表大, **默认优先选它** | 表正着扫会状态爆炸, 反着扫才活得下来 |

命名规矩写在 `re2set_common.go` 头注 (只写一遍, 三个类型的 doc 都引它):
第一个字母 = 第一趟方向 (`f`/`r`), 后面是去重叠口径, 锚**终点**的用 `e` 标出来, 不标的锚起点。

🔴 `rrl` 和 `frel` 都带个 `r`, 锚的坐标却不一样。**别把 `frel` 读成 "rightmost-longest"** ——
那个名字在本库里是 `rrl` 的口径。

🔴 三个类型的**函数签名同形**, 但它们**不是**一个 Go `interface`, 本库也不打算定义一个。
同形只为好学好换; 真让它们泛型可替换, "抄一份换个类型名"就从"人抄错"变成"代码天然踩",
而三者的**输出顺序本来就不一样**。

## 2. 三个口径的定义, 逐字读

### `Re2Set_fll_t` —— 正向 · leftmost-longest

> 在还没被占掉的那段正文里, 反复取**起点最靠左**的那个匹配, 同起点取**最长**, 吐出去,
> 再往右接着找。

对外保证:

1. `body[Start:End]` 是第 `Index` 条 pattern 的一个**真匹配**;
2. **同一条 pattern** 吐的区间互不相交, 按 `Start` **升序**;
3. 口径是 leftmost-longest, **无条件** —— 没有旋钮, 没有"快而不准"的档。

🔴 ③ **不是**"与 `FindAllStringIndex` 相同"。stdlib 默认那个是 leftmost-**first** (贪心),
两者在"同一起点上贪心先撞到的比最长的短"时给不同的右端。对拍要拿 `Longest()` 那个,
拿默认那个对是**假红**。

怎么补起点 (变长条):
① 从右端 `e` 起, 反向机**种全部活状态**往左走到机器死, 沿途收下**全部**可行前缀起点;
② 把候选**升序**逐个拿正向锚定 longest 搜索去验, 第一个成的就是答案。
升序 ⟹ leftmost; longest 模式 ⟹ longest。定长条 (`min == max`) 走 `Start = End - min`
一句减法, **根本不进正则引擎**。

### `Re2Set_frel_t` —— 正向 · 最右终点最长

> 上界从正文末尾起, 取**终点**最靠右且 `<=` 上界的匹配, 同终点取最长 (= 起点最靠左),
> 收下之后把上界压到它的**起点**, 继续往左。

等价说法: 把正文倒过来看, 它就是普通的 leftmost-longest。

保证①②与 `fll` 一字不差 (同样是 `Start` 升序), ③ 换成"最右终点最长, 无条件"。

它比 `fll` 省在哪: 补起点不再"逐个右端各问一次回看", 而是靠 DFA 状态里的
**per-pattern 存活位** (`State::live_`) 把一条 pattern 的命中切成若干**分量** ——
某个偏移上这条 pattern 一个活线程都没有, 就说明没有它的匹配能跨过这个偏移, 两边互相独立。
一处命中定下来之后下一处的搜索上界立刻压到它的左端, 所以**一个分量里问几次锚定 =
这个分量里真的有几处不重叠的匹配**。

### `Re2Set_rrl_t` —— 反向 · rightmost-longest

> 在还没被占掉的那段正文里, 反复取**起点最靠右**的那个匹配, 同起点取**最长**, 吐出去,
> 再往左接着找。

保证①与 `fll` 相同, ② 是"互不相交, 按 `Start` **降序**"。

🔴 **降序**是它与 `fll` 最容易写错的差别。要升序是调用方那边一句 reverse 的事;
库这边翻就得**攒**, 而"一个字节都不攒"正是这条路存在的理由。

🔴 **反向是更好做的方向, 不是更难做的。** 正向那一趟 DFA 交出来的是匹配的**右端**,
起点得回推 (上面 `fll` 那两步就是干这个的); 反向交出来的是**左端 = 起点**, 而
leftmost/rightmost-longest 这个口径本来就**定义在起点上** —— 所以这一侧连"收候选再逐个验"
那一步都没有, 每处命中恒等于**一趟正向锚定**, 代价 = 这处命中有多长, 与正文长度无关。
它也顺手接住了正向那一档最难受的一族: **长度没有上界**的 pattern (邮箱那种)。

🔴 **为什么从右往左仍然一个字节都不用攒**: 因为口径也跟着翻了。
想在反向扫描上给 leftmost-longest 就**必须攒** —— 手上这一处随时可能被更靠左、还没扫到的
那一处整个吃掉, 无上界的那族得攒到整篇扫完, 内存就跟着正文长, 正是这一层存在的理由被赔掉。
改成 rightmost-longest 这件事就没了: 从右往左走, **第一个见到的起点就是最终答案**。

## 3. 同一个输入, 三种答案

| 正文 | pattern | `fll` | `frel` | `rrl` | stdlib `Longest()` |
|---|---|---|---|---|---|
| `aaa` | `aa\|a` | `[0,2) [2,3)` | `[0,1) [1,3)` | `[2,3) [1,2) [0,1)` | `[0,2) [2,3)` |
| `abc` | `b\|abc` | `[0,3)` `"abc"` | `[0,3)` `"abc"` | `[1,2)` `"b"` | `[0,3)` `"abc"` |
| `abab` | `a\|ab` | `[0,2) [2,4)` | `[0,2) [2,4)` | `[2,4) [0,2)` | `[0,2) [2,4)` |
| `aab` | `ab\|b` | `[1,3)` `"ab"` | `[1,3)` `"ab"` | `[2,3)` `"b"` | `[1,3)` `"ab"` |

怎么读这张表:

- **第 1 行**是三种口径的自检格: 一条 `aa|a` 撞 `"aaa"`, 三个口径给**三个不同**的答案。
  库里几处对拍都拿这一格当"判据没失效"的哨兵 —— 三个答案要是相同, 整个对拍就是空跑。
- **第 2 行**是 `frel` 选终点不选起点的理由: 锚起点 (`rrl`) 会把 `"abc"` 截成中间那个 `"b"`。
- **第 3 行**说明 `fll` 与 `rrl` 在**两个真匹配不交叠**的地方逐处相同, 只是顺序反了。
- **第 4 行**才是它们**真的**分家的地方。

三者都满足同一件事: **每段都是真匹配 · 同一条 pattern 内互不相交 · 不整段静默漏掉**。
差别只发生在"两个真匹配互相交叠"的地方。

🔴 ② 只管**单条**。两条**不同的** pattern 在同一片正文上照样重叠 —— 那不是重复,
是两个问题各要一个答案。实例: `"Passport No: A123456780"` 上
`\b[A-Z][12]\d{8}\b` 与 `(?i)\b[A-Z]{1,2}\d{7,9}[A-Z]?\b` 抢**完全同一段**;
合并的话谁赢只由常量写在第几行决定, 而谁能活要等下游把校验位跑完才知道 —— 库这层两样都不知道。
真语料上被 ≥2 条 pattern 盖住的字节占已盖住字节的 **55.6%**, 所以这是常态不是边角。

## 4. 🔴 leftmost-longest 不是"最好的那个"

这一节单独立着, 因为这是最容易搞错的一件事。

**① 它不是"最不容易截短命中"的那个。**
"命中被截短 ⟹ 拿去过校验位 (mod-10 / Luhn / mod-97) 会失败 ⟹ 下游把真命中自己毙掉 = 无声漏报"
是这一族接口最要命的伤。防住这件事的是"**别锚起点去猜终点**",
而 `fll`(锚最左起点 + 取最长终点)和 `frel`(锚最右终点 + 取最长起点)**都**防住了;
真会截短的是 2026-08-28 删掉的那条老路 `spanFast` ——
它只种 accept 回推一个起点, 在 11 份 100MB 语料上量出 **37 处**错边界
(`784-1985-1234567-1` 被截成 `1985-1234567-1`, `<<SYS>>` 被截成 `<SYS>`)。
`rrl` 锚的是起点, 所以在 `b|abc` 这种形状上确实会给中间那个 `"b"` ——
**这不是 bug, 是口径**, 选它之前先确认你的下游不吃这个亏。

**② 它不是最快的那个。** 见 §5: 12 格里 11 格 `frel` 比 `fll` 快, 补起点那一层稳定 2.2~2.4 倍。

**③ 它不一定是你的需求。**
判据只有一条: **你的下游是不是真的要"和 stdlib 逐字节相同"?**

- 要 (拿区间去和另一套用 `regexp` 写的实现对账 / 有现成的黄金用例) → `fll`, 没得选。
- 不要, 只是"把这片正文里的东西都框出来"(脱敏 · 定位 · 计数 · 高亮) → **三个都行**,
  按 §6 挑最便宜的那个。

## 5. 性能: 实测账

### 5.0 三条路共有的地板

一遍正向/反向 `kManyMatch` DFA 扫描, 谁都要付。三个类型的差别**全在补端点那一层**。
所以下面所有对比都把"地板"和"补起点层"分开列 —— 只看总时间会把结论稀释掉。

### 5.1 有这一层 vs 没有这一层 (对老的两段式)

> 🔴 下面两组数出自**不同的表和不同的语料**, 不要横向比。

一张 90 条的生产形状表 (52 条要区间), 7.03MB 正文, 同一次跑里量三档:

| 走法 | 整条腿 | 对老路 |
|---|---|---|
| 老路 (`Match` + 每条命中各扫一遍全文 `FindAll`) | 78.2 ms | 1.00× |
| `fll` (要区间) | 43.8 ms | **1.79×** |
| 只要"命中没命中" (全表 `ExistOnly`) | 21.9 ms | 3.57× |

一张 155 条的真实规则表, 6.4MB 正文 (47 条命中, 稳态, 64MB 预算):

| | 整条腿 | Go 堆分配 |
|---|---|---|
| 老路 | 369.3 ms | 4.0 MB / 2252 objects |
| `fll` | **24.6 ms** (**15.0×**) | ~0 / 146 objects |

按正文大小看这条曲线: ≤8KB 打平 (1.0×) · 32KB 3.1× · 512KB 6.1× · 2MB 14×。
量到的**最差一格是 0.94×**(慢 6%): 人造串每 38 字节一处命中, 几乎每个字节都在某个匹配里,
每处两次过桥没有东西可摊。

🔴 这两组数都是 2026-08-28 换路**之前**量的。它们回答的是另一个问题 ——
**有这一层比没有这一层好多少**(相对老的「Match + 每条命中各扫一遍全文」), 而那个
比值换路之后只涨没跌。换路之后的数在 `doc/补起点换路的实测账_20260828.txt`。

### 5.2 `frel` vs `fll`

**先说怎么量, 因为量错了什么结论都得不出来。**
🔴🔴 **一个二进制里的数字不作数, 必须扫代码布局取最小值。**
这几条 DFA 热循环对代码布局极其敏感 —— 同一份 C++, Go 那侧只多编进一个**没人调用**的
函数, 数字就能翻一倍。2026-09-01 实测 8 个布局:

```
zero/Re2SetFrel      198  98  99  98  97  98  99  98   (us)
zero/Re2SetFll        99 143 143 142 143 145 139 143
```

两个变体的**最小值**都是 ~98us, 但任何单个二进制都会给出一个 1.5~2 倍的假差别,
而且谁快谁慢跟着布局翻面。所以量法是: `for k in 0..7` 各塞 k 个没用的函数编一个二进制,
每个变体**各取最小值**再比。(`doc/set性能优化经验.txt` 早写了这台机 ±20%~2 倍的抖动,
这是目前见过最狠的一例。)

**(a) 10 条手造 pattern · 64KiB · 8 个布局取最小 (µs)**

| 语料 | 老的两段式 | `fll` | `frel` |
|---|---|---|---|
| zero (一条都不命中) | 97.5 | 98.5 | **97.2** |
| few (39 处稀疏命中) | 430.9 | 104.8 | **104.3** |
| most (全小写最坏输入) | 598.9 | **478.7** | 575.6 |

- **zero** —— 产线绝大多数正文长这样。`frel` 与**完全不开分量档的裸扫**逐 µs 相同:
  "存活位切分量"这套在没有命中的正文上**真的一分钱不花**(空闲档一个字节都不读存活位,
  第一次命中才换到盯着档)。
- **few** —— 对老路 4.13 倍, 省掉的正是那 1+k 遍全文重扫。
- **most** —— 语料全小写无空格, `[a-z]{4,}` 一口吃掉整篇 ⟹ 这条 pattern 从头到尾**不断气**,
  整篇就是**一个分量**, 每个字节都在盯着档里读一次存活位。这一档 `frel` 比 `fll` 慢 17%。
  真语料不长这样。

**(b) 🔴 上面那三档只有 10 条手造 pattern, 会低估。换成真实规则表是 1.4~2.2 倍。**

三张真实规则表 (368 条字面量按形状分成 cred 64 条 / prompt 31 条 / body 160 条),
256KiB 正文 × 四档命中密度, 同样 8 个布局各取最小 (ms):

| 表/密度 | 地板 | `fll` 总 | `frel` 总 | `fll` 补 | `frel` 补 | 总 `fll/frel` | 补 `fll/frel` |
|---|---|---|---|---|---|---|---|
| cred 0% | 0.38 | 0.38 | 0.36 | 0.00 | -0.02 | 1.06× | — |
| cred 1% | 0.40 | 0.45 | 0.42 | 0.05 | 0.02 | 1.07× | 2.50× |
| cred 10% | 0.48 | 0.97 | 0.70 | 0.49 | 0.22 | 1.39× | 2.23× |
| cred 90% | 1.00 | 5.42 | 3.00 | 4.42 | 2.00 | 1.81× | 2.21× |
| prompt 0% | 0.38 | 0.38 | 0.36 | 0.00 | -0.02 | 1.06× | — |
| **prompt 1%** | 0.40 | **0.52** | 0.59 | 0.12 | 0.19 | **0.88×** | **0.63×** |
| prompt 10% | 0.50 | 1.68 | 1.15 | 1.18 | 0.65 | 1.46× | 1.82× |
| prompt 90% | 0.97 | 11.45 | 5.60 | 10.48 | 4.63 | 2.04× | 2.26× |
| body 0% | 1.85 | 33.53 | 14.94 | 31.68 | 13.09 | 2.24× | 2.42× |
| body 1% | 1.96 | 35.18 | 15.68 | 33.22 | 13.72 | 2.24× | 2.42× |
| body 10% | 2.35 | 37.67 | 17.08 | 35.32 | 14.73 | 2.21× | 2.40× |
| body 90% | 4.21 | 53.06 | 26.38 | 48.85 | 22.17 | 2.01× | 2.20× |

(地板 = 谁都要付的那一趟正向 set 扫 · 补 = 总 − 地板, 即补起点这一层的钱)

- **12 格里 11 格 `frel` 更快**, 端到端 1.06~2.24 倍, 补起点这一层稳定 **2.2~2.4 倍**。
  省在哪一句话说清: `fll` **每个右端**问一次反向锚定, `frel` **每个分量**问一次
  (body 90%: 25.4 万个右端 vs 14.5 万个分量)。
- **唯一慢的一格是 prompt 1%** (0.19ms vs 0.12ms, 差 0.07ms)。这张表全是顶层交替支多 /
  带非 ASCII 的形状, 命中一稀 (528 处) 分量几乎一处一个, 省不出锚定次数, 白付切分量的记账。
  命中一密 (10%/90%) 就反超到 1.8~2.3 倍。
- **body 表四档都是 2.2 倍上下**, 而且 0% 那行也有 20 万处命中 —— 160 条的混合表连填充词
  都能命中。这就是产线大表的常态。

### 5.3 `rrl` 的账: 它省的不是这一层, 是**方向**

`rrl` 与另外两个不在一条赛道上。它的价值不在"补起点便宜"(虽然它确实最便宜 ——
每处命中恒等于一趟锚定, 没有候选可验, 没有分量可切), 而在于**有一族表正着扫根本活不下来**:

`S B{m,n} L` —— 起始类**严格窄于**重复类、结尾是个字面量 —— 这一族正向的状态数对计数上界
**指数增长**, 反着读就塌回线性。同一条 pattern 实测:

| | 状态数 | 状态区 |
|---|---|---|
| 正向 | 66 572 | 8.39 MB |
| 反向 | **42** | **0.07 MB** |

状态数差 **1585 倍**。这种表本来就该反着扫, 而在这一层出现之前, 反着扫只能当个**布尔门**用
(`Match` 说哪几条命中, 要位置还得再正着扫一遍全文 —— 正好又是 1+k 遍那笔账)。

🔴 **但反向 set 本身仍然该是"一条一个"或者一张很小的表。**
set 里的状态数是**相乘**的: 真实规则表实测 155 条**正向** set 扫 6.4MB = 18ms / 零 flush;
同一张表**反向** = **65 秒** / arena 顶满 254MB 还在 flush。
`rrl` 不改变这件事 —— 它只是把"扫出来的左端"补成完整区间。挂新表之前先量
`GetMemInfo().Flushes`。

## 6. 怎么选 (照这个顺序问)

```
① 我的表正着扫会不会状态爆炸? (S B{m,n} L 那一族 / 量出来正向 flush 停不下来)
     会  → 反向, 用 Re2Set_rrl_t。记得 Start 是【降序】, 且反向表要小。
     不会 → ②

② 下游是不是真的要"和 stdlib re.Longest().FindAllStringIndex 逐字节相同"?
     是  → Re2Set_fll_t。没得选, 这是唯一给这条保证的。
     不是 → ③

③ 默认 Re2Set_frel_t。
     例外只有一个: 表全是"顶层交替支很多"的形状 且 命中很稀 —— 那一档 fll 略快 (实测 0.88×)。
     🔴 不确定就两个都量一遍, 别照着这一页猜: 这两条路的差距是【表的形状 × 命中密度】
        的函数, 换张表就换个数。量法见 §5.2 那段"必须扫布局取最小值"。
```

还有一个与三选一无关、但**先该问**的问题:

🔴 **这一条 pattern 到底要不要位置?**
`Re2Set_req_t.ExistOnlyIndexList` 里点名的那几条只报"命中没命中", 一处区间都不收口、
一次端点都不补 —— 而**补端点正是贵的那一半**。大表里很多条天生就是纯布尔
("这类内容出现过没有"), 从来没人问它在哪。实测某张表上光两条这样的 pattern 就占了
**57%** 的游程。

🔴 在回调里过滤**替代不了**它: 到那时钱已经花完了。

🔴 它是**每遍**的参数, 不是建对象时定死的属性 —— "先问有没有, 有才问在哪"是这一层最自然的
用法, 一个对象就能两种问法, 不必开两个对象两份缓存。

## 7. 怎么用

三个类型的用法**同形**, 学会一个另外两个不用再学。

### 7.1 建对象: 【进程级】, 建一次留着

```go
set, _ := hgmLibre2.NewRegexpSet(patterns)   // 包级变量, 建一次
s, err := set.NewRe2Set_fll()                // 一个策略一份, 跟策略同生共死
defer s.Close()
```

🔴 **别每遍新建。** 对象身上常驻的是"补端点用的单条正向/反向对象缓存"(惰性建,
最大那张 158 条生产规则表实测 **9.6MB**, 其中 89 条被真问到过位置)。每遍新建 =
每篇正文把那 9.6MB 重编一遍再扔掉。量它用 `GetViableOneStats()`。

🔴 换策略的时候 `Close()` 旧的。native 那侧是**引用计数**, 手上还在跑的那几遍照样安全跑完,
最后一个走的人关灯。忘了 `Close` 也不漏 (有 finalizer 兜底), 只是释放时机交给了 GC。

三个构造函数只差挂在谁身上:

```go
fll,  _ := set.NewRe2Set_fll()    // *RegexpSet
frel, _ := set.NewRe2Set_frel()   // *RegexpSet
rrl,  _ := rset.NewRe2Set_rrl()   // *RegexpSetReverse (NewRegexpSetReverseMaxMem 建的)
```

### 7.2 扫一遍

请求结构 `Re2Set_req_t` **按值传**, 三个类型的 `Scan` 吃的是同一个。
零值合法, 意思是"什么都不要": 三个回调一个都没有 ⟹ 正文一遍都不扫, 一个字节都不分配。

```go
alloc := hgmLibre2.NewRe2Set_alloc()   // 每个 goroutine 自己持有一个, 长期复用

err := s.Scan(hgmLibre2.Re2Set_req_t{
    Body:               body,
    Allocer:            alloc,
    ExistOnlyIndexList: []int32{3, 7},   // 这几条只要"命中没命中"

    StartEndResultFn: func(batch []hgmLibre2.Re2Set_startEnd_t) bool {
        for _, m := range batch {
            // body[m.Start:m.End] 是第 m.Index 条 pattern 的一个真匹配
            handle(m.Index, body[m.Start:m.End])
        }
        return true      // 返回 false = 提前收工 (不算错, Scan 返回 nil)
    },

    HitIndexResultFn: func(ids []int32) {
        // 扫完一次性交: 全表命中位 (升序 · 不重复 · 含 ExistOnly 那几条)
        // 等同于 set.Match 会给的那张表
    },

    StatsResultFn: func(st hgmLibre2.Re2Set_stats_t) {
        // 配了才收, 生产路径上不配它一个 cgo 调用都不多花。见 §8
    },
})
```

🔴 **交给回调的切片就是 `Allocer` 里那块缓冲本身**, 下一批**原地覆写**。要留就自己
`append` 走。这也是为什么这个接口是**批式**而不是"最后给我一个数组": 游程条数跟正文长度
成正比 (真实规则表实测约 **30 741 条/MB**, 200MB 正文就是 47MB), 攒起来等于让内存跟着
正文长。`Scan` 自己无论正文多长都只占固定的 12KB 输出缓冲 + 底下 48KB 游程缓冲。

🔴 各条 pattern 的结果是**交错**着来的 (按区间收口的先后), **不按 pattern 分组** ——
同一条**内部**才有序。想按条归拢是调用方那边一句 `append` 的事; 库这边归拢就得攒 = 又是缓冲。

### 7.3 并发

```
一个 Re2Set_*_t 对象   →  可以【并发 Scan】(Scan 开头拿一下读锁把 native 暂存开出来就放手)
一个 Re2Set_alloc_t    →  【不是】并发安全的, 一个 goroutine 一个
背后那个 RegexpSet     →  只读, 随便共享
```

🔴 `Re2Set_alloc_t` 是**纯 Go 缓冲**, 里面一个 native 句柄都没有 —— 所以同一个 alloc
可以**跨对象、跨表**自由传, 不存在"这个 alloc 不是这张表的"这种运行期错误。

### 7.4 出错了怎么办: 只有一种交代

🔴 **`Scan` 返回 `err` = 这一遍整个作废**, 连已经交出去的批次也不算数。整篇走老路 `FindAll`。

**没有**"这几条没给全你自己补"的中间态。`err` 的来由全是 `maxMem` 配小了
(扫描那遍 DFA 放弃 / 补端点的单条对象编不出来 / 回推放弃), 外加一种"游程不按扫描方向单调"
—— 那是**本库的不变量崩了**, 是 bug, 走同一个 `err` 报出来而不是咽掉。

为什么不做"部分成功": 一个**调用方造不出来**的错误码不该出现在返回值里。
它逼出这条链 —— 调用方必须写兜底 → 兜底跑不到 → 跑不到就没法测 → 没法测的代码基本是错的
→ 真轮到它的那天, 执行走进一段从来没执行过的路。那比没有兜底、整遍失败更糟。

## 8. 怎么量自己这一遍花了多少

配上 `StatsResultFn` 就有 `Re2Set_stats_t`:

| 字段 | 含义 | 哪几个类型会涨 |
|---|---|---|
| `Walks` | 锚定回推了几趟 | 三个都涨 (`fll` = 处理了几个没被游标盖住的右端; `rrl`/`frel` = 每处命中一趟) |
| `Cands` | 这些趟一共给出多少候选起点 | **只有 `fll`**, 另外两个恒 0 |
| `Tries` | 一共拿锚定搜索验了几次 (`fll`: `<= Cands`, 命中即停) | 三个都涨 |
| `Emits` | 交出去几处区间 (含定长条) | 三个都涨 |
| `NSeg` | 存活位切出来几个分量 | `fll` / `frel` (`rrl` 不切分量, 恒 0) |
| `UsedPeak` | native 游程里真正装着结束位置的字节峰值 | `fll` / `frel` |
| `HeapPeak` | 这一遍为游程数组真实持有的堆字节高水位 | `fll` / `frel` |

要盯的就两个比值:

- **`Tries/Walks`** (`fll` 这条路便不便宜的**唯一**那个数) —— `1.00` = 升序第一个候选就是答案,
  一次假候选都没验。2026-08-28 实测 **11 份 100MB 真语料 × 9 张生产规则表 = 99 格, 全是 1.00**。
  最坏形状会到 2.00 (`a|[ab]+c`: 每个右端两个候选, 第一个必然验不过)。
- **`Tries/NSeg`** (`frel`) —— 平均每个分量里有几处不重叠的匹配, 越接近 1 说明存活位把分量
  切得越干净, 一个分量一趟锚定就结完。

🔴 **别拿 `Tries/Emits` 当"平均验了几次"**: 前三个字段只统计变长条 (定长条走 `e-minL`
减法, 一次回看都不做, 不进分母), 而 `Emits` 把定长条也数进去了, 会被稀释。

常驻内存单独量: `Re2Set_fll_t.GetViableOneStats()` 报**已经建出来**的那些单条反向 set 的
条数 / 状态数 / 状态区字节。惰性建 ⟹ 没被真问过位置的 pattern 一条都不占。

## 9. 这些口径是怎么钉住的

三条路各有自己的**穷举判据**, 都不依赖本库 (只用 stdlib), 而且都带**自检格**:

| 类型 | 判据 | 在哪 |
|---|---|---|
| `fll` | `re.Longest().FindAllStringIndex` 逐字节 (300 轮 AST 生成语料) | `re2set_fll_astfuzz_test.go` · `re2set_fll_test.go` |
| `frel` | 穷举 `\A(?:pat)\z` 扫遍每个 `(e, s)` 的最右终点最长序列 | `re2set_frel_test.go` (`frelBrute`) |
| `rrl` | 穷举的 rightmost-longest 不重叠序列 | `re2set_rrl_test.go` (`rrlBrute`) |

🔴 **语料必须从 pattern 自己的 `regexp/syntax` AST 生成再拌噪声, 不能纯随机撒字节** ——
纯随机正文上这批 pattern 一处都撞不上, 那是**空转绿**。测试末尾"命中数少于 N 就 Fatal"
是这件事的哨兵。

🔴 **自检格**: `aa|a` 撞 `"aaa"` 必须给出**三个不同**的答案 (见 §3 第 1 行),
否则整个对比是个 no-op。`frel` 的判据里还额外钉了"判据本身不懂分量" ——
所以它同时也证明了"切分量不改变答案"。

🔴 **对拍不能按吐出来的先后流式比。** 对外保证只管到"同一条 pattern 内有序",
跨 pattern 的先后**没有保证** —— 照吐出顺序直接比, 量到的是"排列不同"而不是"区间不同"
(实测能把 8MB 语料上的 8.5 万处全判成不一致, 排完序一处不差)。
比之前先按 `(条, Lo, Hi)` 排成规范序。

## 10. 再往下一层: 只要端点, 自己定去重叠规则

三个类型都搭在同一个底座上: `RegexpSet.FindAllIndex` / `RegexpSetReverse.FindAllIndex` ——
一遍扫正文, 一批一批交出**端点游程** `(ReIndex, Lo, Hi)`: 第 `ReIndex` 条 pattern 的匹配
端点落在 `Lo..Hi` 的**每一个**值上 (原文字节偏移, **两端都含**)。

- 正向 set: 端点 = 匹配**右端**(不含);
- 反向 set: 端点 = 匹配**左端**(含)。

补另一端用 `ResolveSpan` / `ResolveSpanWithin`: **单点、锚定、代价与正文长度无关** ——
1KB 和 6.4MB 的正文上问同一句话价钱一样。

🔴 **别拿反向 `FindAllIndex` 去扫一遍全文来补另一端**: 155 条反向表扫 6.4MB 是 65 秒
(正向 18ms); 拆成一条一条反着扫倒是便宜, 可命中 k 条就是 k 遍全文 —— 正好是这一层存在的
意义 (把 1+k 遍压成 1 遍) 被原样赔回去。

🔴 **也别在 Go 那侧自己补**: 自己补只能另编一条 `\A(?:pat)` 的锚定正则, 每条一个 `Regexp`
对象、一份独立 DFA 缓存, 还得手工保证它和 set 里那条语义一致; 而**非锚定**的补法
(拿原正则去扫 `text[from:]`) 更糟 —— `.*?` 前缀让每个位置都能当起点, 状态数对计数上界
指数增长。

什么时候真该下到这一层: 你的去重叠规则**这三种都不是**
(比如"跨 pattern 按优先级贪心"、"相交即全丢"、"要重叠的全部保留")。
那些是调用方的业务, 这一层不替它决定。
